# 開発の流れ（全自動パイプライン）

人間がやるのは「何を作るか決める」ことだけ。あとはAIとGitHub Actionsが進め、人間の判断が要るときだけ止まって知らせる。

```
Issueを作る（メモ）。ラベルが無ければ自動で ai:plan が付く   intake.yml（見落としは watchdog.yml が拾う）
  → 企画AIが清書して ai:implement を付ける        claude-plan.yml
     （進行中の作業とぶつかると企画AIが判断したら ai:queue で順番待ち。別の場所なら最大3つまで（`MAX_PARALLEL`、既定 3。上限は持ち主の全部のリポジトリで合わせて数える）並列）
  → 実装AIがブランチに実装し、PRを自動で作る        claude-implement.yml
  → CI（pipeline.json の checks。無ければ型チェック・リント・テスト・ビルド。package-lock.json があれば npm audit --omit=dev --audit-level=high も。テンプレートでは落とし、配り先のアプリでは警告だけ）と、レビューAI（ai:review）を同時に始める
                                                    ci.yml・claude-review.yml（PRを作った・直して push した時点で）
  → main が進んでいたら取り込んでCIをやり直す         pipeline.yml
  → CIとレビューの両方が通ったら（後に終わった方が判断する）
  → 指摘なし：自動でマージ → 公開（Vercel／App Runner／GitHub Releases／Expo）   pipeline.yml → deploy.yml
     指摘あり／CI失敗：AIが直す（@claude、3回目は opus）→ CIから   pipeline.yml → claude-mention.yml
  → 公開されたらスマホに通知                        deploy-notify.yml
  → 順番待ち（ai:queue）があれば次を始める           queue.yml

CIとレビューAIを同時に動かす（#119）：レビューはCIを待たずに始める（CIの中央値 2.8分を待たない）。例外（#204）：見た目のテストがあり（PRのブランチの `package.json` の `test:visual`、または `pipeline.json` の `checks`）、PRの本文に `visual:update` があるPRは、最初のレビューをCIのあとに回す（`open-pr.sh`・`after-mention.sh` が `defer_review_for_visual` で判定し、`request_review` を呼ばない。本文はその時点の最新を読み直す。ブランチの中身が読めないときは「見た目のテストは無い」と扱い、今までどおり同時に始める）。理由：こうしたPRは、ほぼ必ずCIが見た目のテストだけで落ち、基準の画像を撮り直したあとにCIとレビューが最初からやり直されるため、最初のレビューは必ず捨てられる。後回しにしても止まらない：CIが通れば `after-ci.sh` が `ai:review` を付ける／見た目のテストだけが落ちれば撮り直し、ほかの理由で落ちれば修正AIが直し、そのpushのあとのCIで同じ流れに戻る／途中で取り消されても見張り役の 3.4 が拾う。CIが落ちたら、同じコミットのレビューAIは取り消す（after-ci.sh の cancel_running_review）。同じコミットに、CIとレビューの両方から「直して」を二重に頼まない（fix_requested_for）。同じブランチを動かす物（修正AI・基準の画像の撮り直し）は、同時に動かさない（下の「修正AIと撮り直しを同時に動かさない」）。CIが後に通ったら、出ていたレビューの結果でマージへ進む（after-ci.sh → after-review.sh。review_state）。CIが途中で取り消されたら（時間切れなど。新しいコミットで取り消された物は除く）、取り消されたジョブを1回だけやり直し、同じコミットでまた取り消されたら `ai:stuck` で人間に回す（黙って止まらない。PR #161）

止まったときの自動再開
  使用量の上限・AIのエラー・時間切れ → ai:retry を付けて、見張り役がやり直す（10回まで）   watchdog.yml
  人間が ai:stuck を外す → 止まった所から続ける（直す回数もリセット）                              resume.yml
```

## ラベル

| ラベル | 付けるのは | 意味 |
| --- | --- | --- |
| `ai:plan` | 受付（intake.yml）。人間が付けてもよい | 企画AIが清書して、実装に回す |
| `ai:skip` | 人間・受付（オーナー以外が作った Issue） | まだ自動で動かさない。Issueを作るとき付けておく。外すと企画に回る（人間の下準備が先に要る物用）。付いている間は、企画のあとの処理も見張り役のやり直しも動かない（下の「安全のしくみ」） |
| `ai:implement` | 人間か企画AI | 実装AIが作業を始める |
| `size:S` / `size:L` | 人間か企画AI | 実装AIのモデルと作業回数の上限を変える（S：haiku・40回、無印：sonnet・60回、L：opus・100回） |
| `ai:review` | パイプライン（人間も可） | レビューAIが確認する |
| `ai:queue` | 企画AI（進行中の作業とぶつかると判断したとき）か人間 | 順番待ち。進行中の作業があっても、並列の上限（既定 3。夜は1など。下の「順番待ちの進め方」）に空きがあり、触るファイルが進行中の物と重ならなければ、実装が始まる（`priority:high` が先、その中は番号の小さい順）。重なる物は、それが終わるまで待つ。企画の段階で止まった物は待たない。まとめて頼んで寝ておける |
| `ai:blocked` | 企画AI（`BLOCKED`） | 他の Issue・PR の完了待ち（その結果や決まりを使う作業。別のリポジトリの作業でもよい）。待ち先はコメントの印 `<!-- blocked-by: owner/repo#N -->`（待ち先ごとに1つ）。見張り役が待ち先を見て、全部閉じたら（マージ・クローズ）`ai:blocked` を外して `ai:plan` に戻す。人間は何もしなくてよい（下の「他の Issue・PR の完了待ち」） |
| `ai:found` | 使ってみる役・監査役（`found-report.sh`） | 使ってみる役（公開後に本番を試す）・監査役（仕様書の食い違いを探す）が見つけて作った Issue の印。`ai:plan` も一緒に付き、いつもの流れに乗る（下の「使ってみる役・監査役」） |
| `priority:high` | 人間 | 急ぎ。順番待ち（`ai:queue`）から先に実装に回す（下の「順番待ちの進め方」） |
| `ai:hold` | 人間か進行役 | 最後のマージだけ人間が押す（大事な変更用）。`.github/`・`.claude/`・`docs/pipeline.md`・`docs/pipeline-setup.md`・`CLAUDE.md`・`AGENTS.md`・`pipeline.json` を触るPRには、進行役が自動で付ける（ただし ai-dev-template 自身は、`.github/scripts/`（テストを含む）・`docs/pipeline.md`・README だけの変更なら付けず、自動でマージする。下の「安全のしくみ」） |
| `ai:retry` | パイプライン | AIが一時的に止まった（使用量の上限など）。見張り役が30分以上あけて自動でやり直す（失敗のコメントに、原因の分類とログのURLが付く）。人間は何もしなくてよい |
| `ai:stuck` | パイプライン | 自動で進められず止まった。人間が確認して、続けるなら外す（外すと自動で再開） |
| `ai:question` | 企画AI・画面案 | 結果が大きく変わる迷い（見た目の方向・画面の構成・挙動・お金・データ・範囲）を、選択式で質問して待っている（コメントの印 `<!-- ai-question -->`）。オーナーがコメントで答えると `answer.yml` が `ai:plan` に戻し、企画AIが答えを使って清書する。閉じた Issue は清書に戻さない（`ai:question` を外すだけ。見張り役も閉じた物の `ai:plan`・`ai:question` を外す）。小さい迷いは聞かずに「仮定」に書く |
| `ai:mocks` | 企画AI | 見た目の大きい作り直し・新しい画面の作業。作る前に `claude-mocks.yml` が、今の画面とデザイン仕様を見てざっくり画面を2案作り（1枚の HTML。画像と HTML は `ai-mocks` ブランチ）、選択肢と質問を書いて `ai:question` で待つ。答えると、企画AIが選んだ画面を「目標の画面」（本文の印 `<!-- ai-mock: … -->`）として清書し、実装AIはそれを `.shots/target/` に受け取って合わせて作る |
| `visual:update` | 進行役（見た目のテストだけが落ち、PRに「見た目を変えた」と書いてあるとき。修正AIが変更なしで終わり、AIの返事・レビューの指摘に撮り直しの依頼があるとき。ほかのチェックも落ちていれば、先にやり直し→修正AIで見た目以外を直してから）か人間 | 見た目のテストの基準の画像を、CIの環境で全部撮り直してPRにコミットする（差が閾値の中で通っていた画像も撮り直すので、古い見た目の画像が残らない。終わると外れる） |

見張り役は、ありえないラベルの組み合わせ（`ai:queue` と `ai:implement`、`ai:plan` と `ai:implement`、記録の無い `ai:retry`、直近7日に閉じた物に残った `ai:stuck`・`ai:retry`・`ai:queue`・`ai:blocked`・`ai:implement`）を直し、その Issue・PR に1行コメントする（1回に20件まで）。

見張り役・順番待ち・再開が読む Issue・PR の一覧は、ページをまたいで全部読む（`api_list`・`gh api --paginate`。1ページ＝100件だけだと、101件目からの物を黙って見落として止まったままになるため）。100件までなら API は1回で、2ページ目からは続きがあるときだけ読む。開いている Issue・PR の一覧は、1回の見張り・1回の順番待ちで1度ずつ読んで使い回す（下の「GitHub API の回数」）。件数や並べ替えが要る所は `api_list`（全部を1つの配列にする）を使う（`--paginate -q` は、ページごとに jq が当たるため）。ワークフローの実行の一覧（新しい順に要る分だけ読む）は、1ページだけ。許可の不足の記録の Issue と、直す Issue（`AIの許可が足りない：…`）は、一覧の先頭100件ではなく、search API（`search/issues`。題名と `repo:` で絞る）で探す。search は作った直後に出ないことがあるので、見つからなければ新しい一覧でも探してから、無ければ作る（`find_issues_by_title`）。

### GitHub API の回数

パイプラインの鍵（GitHub App）の回数制限は、App を入れたアカウントの全部のリポジトリで合わせて、REST が1時間5000回（agent-desk の画面が読む GraphQL は、別の枠で1時間5000点）。リポジトリが増えると1つあたりの分け前が減るので、いちばん回数を使う見張り役と順番待ちは、次の2つで回数を抑える（2026年11月18日、12個のリポジトリで上限に届いたため。見張り役だけで1時間に約2000〜3000回使っていた）。

- **見張り役を間引く**（`watchdog.sh` の 0）：ほかのワークフローが終わって起きたとき（`workflow_run`）は、同じ時間の枠（時計を10分ごとに区切った枠。環境変数 `WATCHDOG_SLOT_MIN`）で、自分より前に始まった見張りがもう成功していれば、何もせず終わる（`watchdog_slot_taken`）。止まりの判定は「5〜45分動きが無い」なので、数分おきに見直しても結果は変わらない。枠の中で最初に成功する見張りは、必ず全部を見る（失敗・取り消し・飛ばされた実行は数えない）。間引いた回も、やり直しと `ai:hold` が外れる時刻の目覚ましだけはかける（開いている一覧の読み2回ほど。目覚ましをかけるのは見張り役だけで、かけ忘れると次の定期の起動まで止まるため）。ただし、期限の来たやり直し（`retry_due_at` が今以前の `ai:retry`。`ai:stuck`・`ai:skip` の物は除く）か、順番待ち（`ai:queue`）があって `HOLD_BLOCK_MIN` を過ぎたマージ待ち（`hold_prs` が `expired`）があれば、間引かずに全部を見る（`watchdog.sh` の `due_work_pending`。目覚ましで起きた見張りが取り消されて、代わりの回が間引かれても、期限の来た物を取りこぼさないため。一覧は開いている一覧の写しから読み、期限の来た物が無ければ今までどおり間引く）。定期の起動・目覚まし（`retry-timer.yml`）・手で動かしたときは、いつも全部見る。前の見張りの一覧はワークフローのトークン（`READ_TOKEN`。回数制限はリポジトリごとに別）で読み、読めなければ間引かない。作業が続くリポジトリでも、全部を見るのは1時間に6回＋定期の2回ほどになる
- **一覧の写し**（`pipeline-lib.sh` の `use_open_snapshot`。`watchdog.sh` と `queue-next.sh` が最初に呼ぶ）：開いている Issue・PR の一覧（ラベル・本文つき）と開いているPRの一覧を1回ずつ読み、その実行の間は「`ai:○○` が付いた Issue の一覧」（`open_numbers_with_label`・`open_items_json`）・「このラベルが付いているか」（`has_label`）・Issue の本文（`issue_body`）・開いているPR（`open_pulls_json`）を、API を呼ばずに写しから答える。人間のマージ待ちのPR（`hold_prs`）も、1回の実行で1度だけ調べる。開いているPRが6つのリポジトリで、見張り1回の API は約110〜170回 → 約25〜30回、何も無いリポジトリで16回 → 6回
  - 自分のラベルの付け外し（`add_label`・`remove_label`・`take_label`）は写しにも反映する。ラベルを外せたか分からないとき（404 以外の失敗）は写しを捨て、そのあとは、その都度 API から読む。別のスクリプトを呼んだあと（`after-ci.sh`・`after-review.sh`）は、写しを読み直す
  - 写しに無い番号（閉じている・あとから作られた）と、写しを読めなかったときは、今までどおり API から読む（読めなかったのを「ラベル無し」と取り違えない決まりも、今までどおり）
  - 写しは実行の最初の時点の物なので、実行の途中（長くて1〜2分）に人間やほかのワークフローが付けたラベルは、次の見張りで見る。順番待ちを始める所（`take_label`。同時に動いた2つの片方だけが進める）と、止まりの判定に使う更新時刻（`issue_idle_min`）は、写しを使わず毎回 API で確かめる
  - 進行役（`after-ci.sh` など）・再開・受付は写しを使わない（1回の実行で読む数が少なく、直前の状態で判断したいため）

## 人間に回る（止まる）とき

- 企画AIが「人間にしかできない作業」が要ると判断した（依存パッケージの追加、`.github/`・`docs/pipeline.md`・CLAUDE.md の変更、秘密情報の登録、外部サービスの設定。Issueに、してほしいことが書かれる。そのコメントの1行目は `<!-- human-request -->`、2行目が要点の1文で、agent-desk の「あなたの番」にはこの1文が出る）。AIのPRにも、ワークフローの差分のように人間しか当てられない物があると、本文に「人間にお願いしたいこと」の節（`##`・`###` の見出し）が付く。その節があるあいだは、PRの作成直後と、レビューのあと・マージの判断の前（`defer_close_for_human_request`）に、本文の `Closes/Fixes/Resolves #N` を `Refs #N` に書き換え、マージしても元のIssueを閉じない。Issueには上と同じ形（1行目 `<!-- human-request -->`、2行目に「PR #○ の『人間にお願いしたいこと』を当ててください。当てたらこのIssueを閉じてください」、その下にPRへのリンクと節。同じPRには印 `<!-- human-request-pr: #番号 -->` で1回だけ）のコメントを書き、進行のラベルを外して待ちの印 `ai:skip` を付ける。人間が当ててIssueを閉じる（自動では閉じない）。意図が読み取れないだけなら止まらず、AIが無難に仮決めして「### 仮定」に書く。大きすぎるときは、最初の分だけをこのIssueにして、残りは新しいIssueとして自動で作る
- 実装AIが正常に終わったのに、変更を残さなかった（拒否された操作が無いとき。コメントに、AIが最後に言ったことが書かれる。拒否があったときは、下の「自動でやり直す」）
- `ai:blocked` の待ち先を、60分たっても読めない（別のリポジトリが非公開で、パイプラインの鍵では読めない、など）
- CIの失敗とレビューの指摘を合わせて、AIが3回直しても解決しない（2回は普通のモデル、最後の1回はいちばん強いモデル opus で直す。`MAX_AUTO_FIX`＝2＋1）。修正AIが「PRが更新されたので動かない」と返して何もしなかった依頼と、main とのコンフリクトの解消の依頼は、3回に数えない
- main とのコンフリクトの解消を、AIに3回頼んだあとで、またコンフリクトした（`MAX_CONFLICT_FIX`＝3。Variable で変えられる。直す回数とは別に数える）：「main とのコンフリクトが4回続きました（AIに解消を頼めるのは3回まで。最後の理由：…）」で人間に回す。並列で main が進むたびに、PRの中身と関係なく直す回数が減って、本物の指摘を直せずに止まらないように（agent-desk PR #528：基準の画像だけのコンフリクト2回で直す回数を使い切り、そのあとの指摘を直せずに止まった）。数え方は、依頼のコメントの印で分ける：コンフリクトの解消の依頼には `<!-- auto-fix -->` に加えて `<!-- auto-fix-kind: conflict -->` を付け、`count_auto_fix PR番号 conflict` はこの印のある依頼だけを、`count_auto_fix PR番号`（`fix`）は無い依頼だけを数える（人間が `ai:stuck` を外した後から。数え方そのものは `count_auto_fix_in`）。コンフリクトの解消は強いモデルを使わない（文の書き方の「n/3」も別：「自動の依頼・コンフリクトの解消 n/3。直す回数には数えません」）
- 直すよう頼んだのに、AIが変更を入れなかった（指摘が誤りだと判断した、など）
- レビューAIがエラーで止まった
- CI 以外のチェック（Vercel など）が、時間をおいて2回確かめ直しても通らない（下の「自動でやり直す」の「CI 以外のチェックが通っていない」）
- `ai:hold` のPRで、CIもレビューもOKになった
- AIが作業回数の上限（`--max-turns`）で止まり、1回やり直しても、また上限に届いた（同じ上限で10回やり直しても同じ所で止まり、そのたびに上限いっぱいまでAIを使うため。Issue を小さく分けるか、`size:L` を付ける。`retry_ai_failure`）。企画AIは、上限（30回）に届いたらその場で1回だけ上限を増やして（50回）やり直すので、それでも届いたら、30分後のやり直しはせず、すぐ人間に回す（下の「自動でやり直す」の「企画AIが、作業回数の上限に届いた」）
- CIが終わったPRを、見張り役が1回動かし直しても進まない（下の「自動でやり直す」の「CIは終わっているのに、誰も先へ進めていない」）
- 画面案（`ai:mocks`）のまま止まった Issue を、見張り役が1回やり直しても、また進まない（下の「自動でやり直す」の「画面案のまま、動きが無い」）

直す回数の上限で止まったときのコメントは、`⏸ 自動で進めるのを止めました：AIが3回（最後の1回は強いモデル）直しても解決しませんでした（最後の理由：レビューの指摘が直りませんでした（指摘：src/components/Desk.tsx:313））` の形になる。「最後の理由」は、AIへの依頼文ではなく、人向けの短い1行の文（改行なし）。`request_fix_or_stop` の4番目の引数で呼び出し元が渡す：CIの失敗は「CIが失敗したままです（失敗したチェック：test）」（名前が取れなければカッコごと省く）、レビューの指摘は「レビューの指摘が直りませんでした（指摘：場所）」（場所は行への指摘の最初の1件の `path:line`、無ければまとめの最初のパス。80字まで。分からなければカッコごと省く）、4番目が無い・空なら「AIが直せませんでした」（AIへの依頼文は出さない）。main の取り込みやマージのコンフリクトは、5番目の引数を `conflict` にして（`request_conflict_fix_or_stop`）別の上限で数え、止まったときは `⏸ 自動で進めるのを止めました：main とのコンフリクトが4回続きました（AIに解消を頼めるのは3回まで。最後の理由：main とのコンフリクトが解けませんでした）` の形になる。

止まったら `ai:stuck` が付き、スマホに通知が来る。確認して、続けるなら `ai:stuck` を外す。外すと resume.yml が、そのときのCIの状態から自動で続ける（通っていればレビューへ、落ちていればAIが直す。AIに直させる回数もリセットされる）。自分で直す・マージする・閉じるときは、外さなくてよい。

Issue の `ai:stuck` を外したときは、付いているラベルで続きを決める（`resume.sh`）：`ai:plan` なら企画を、`ai:implement` でPRがまだ無ければ実装をやり直す。PRがあって、PRも止まっていれば（PRが止まると、PRと Issue の両方に `ai:stuck` が付く）、PRの `ai:stuck` も外して、PRの続きを始める。作業のラベルが1つも無ければ（企画で人間に回すとき、`ai:plan` は外してある）、企画からやり直す（この Issue を閉じるPRが開いていれば、作業はPRの側で進んでいるので、やり直さない）。`ai:mocks` なら、画面案をもう一度作る（画面案のジョブが動いている間は、何もしない）。待っている物（`ai:queue`・`ai:question`・`ai:blocked`）と `ai:skip` の物は、そのまま。

## 自動でやり直す（人間に回さない）とき

**要点**：一時的かもしれない失敗は、すぐ人間に回さず `ai:retry` を付け、見張り役（watchdog.yml）が失敗から30分以上あけてやり直す。10回やり直しても直らなければ `ai:stuck` で人間に回す。使用量の上限は、回数を使わずに待つ。

見張り役は、定期の起動（`*/30` と書いてあるが、GitHub の都合でほとんど来ない。実際は1日に3〜4回、間隔は数時間あく。当てにしない）に加えて、AIやCIのワークフローが終わるたびにも動く。止まりの検知（企画30分・実装45分・レビュー30分など）は「その時間がたった後に、全部を見る見張りが動く」ことが前提なので、待ちが残っている間は、目覚ましで自分を起こす（下の「待っている間は15分ごとに見る」）。ワークフローが終わるたびの見張りは、10分の枠に1回だけ全部を見て、同じ枠の残りは、止まりの確かめなどは飛ばして、目覚ましをかけるだけで終わる（上の「GitHub API の回数」。枠で見張りが済んだあとに付いた `ai:retry`・`ai:hold` の時刻も、目覚ましで拾う）。待ちが明ける時刻には目覚まし（retry-timer.yml）をかけ、その時刻に自分を起こす（使用量の上限のリセットを待っているときも、定期の起動の遅れに左右されない）。

**待っている間は15分ごとに見る**：見張り役は、次のどれかがあるとき、目覚ましを「いまから `WATCHDOG_HEARTBEAT_MIN` 分後（既定 15）」にもかける（今ある時刻と比べて早い方。目覚ましは1つのまま。すでに同じかそれより早い目覚ましがあればかけ直さず、1回の待ちは `RETRY_TIMER_MAX_MIN` までの上限も今までどおり）。
- `ai:stuck`・`ai:skip` でない `ai:plan`・`ai:implement`・`ai:mocks`・`ai:blocked` の Issue（`ai:blocked` は待ち先が閉じる時刻が読めないので、これで拾う）
- `ai:stuck` でなく、人間のマージ待ち（`ai:hold` のPRで `hold_prs` に出る物）でもない、パイプラインの開いているPR（`claude/` のブランチの物。fork・下書き・配布の `pipeline-sync/` のPRは除く）
- `ai:` のラベルが無い開いている Issue のうち、作って2時間以内の物（オーナー・パイプライン・AIが作った物。企画AIが分けて作った Issue は `github-actions[bot]` 作で受付が動かないので、これで拾う。古いラベル無しの Issue では起こさない）

順番待ち（`ai:queue`）があるときは、並列の上限が変わる次の時刻（`PARALLEL_NIGHT_HOURS` の夜の始まり・終わり、`PARALLEL_OVERRIDE` の期限。`pipeline-lib.sh` の `parallel_next_change` が、`parallel_limit_decide` と同じ設定から求める）の1分後にもかける。ただしこの時刻が `RETRY_TIMER_FAR_MIN` 分（既定45）より先なら、かけるのはテンプレートのリポジトリだけ（目覚ましは待つ間ずっと Actions の同時に動けるジョブの枠を1つ使い、無料のアカウントは全部で20。全部のリポジトリが数時間先の同じ時刻にかけると、枠が埋まって CI や AI が順番待ちになる。11/19 朝に13リポジトリで起きた）。自分に順番待ちが無く、ほかのリポジトリ（`PARALLEL_SCOPE=global` のとき）にだけ順番待ちがあるリポジトリは、この目覚ましをかけない。ただしテンプレートのリポジトリだけは、距離に関係なくかける（全部で枠1つ。起きたテンプレートの見張り役が、ほかのリポジトリの順番待ちを始める）。やり直し待ち・見回り・マージ待ちの外れる時刻は、自分の物だけで決める。何も待っていなければかけない（静かなリポジトリで Actions を回し続けない）。`RETRY_TIMER=off` なら、どちらもかけない。間引いた回（10分の枠が済んだ回）でも、この目覚ましはかける（開いている一覧の写しから答えるので、API は目覚ましの確かめ1回とかける1回しか増えない）。`WATCHDOG_HEARTBEAT_MIN` は環境変数で、ワークフローには書かず、スクリプトの既定値（15）を使う。

- 実装AIが Issue の一部だけを直したPR（本文が `Refs #N` で、`Closes/Fixes/Resolves #N` が無い）がマージされた（自動でも人間でも）：`ai:implement` が残ると、見張り役が「実装AIの終了が確認できない」と誤ってやり直しにするので、`requeue_issue_after_partial_merge`（`pipeline-lib.sh`。`after-review.sh` の自動マージのあとと、`queue-next.sh` の人間のマージのあとで呼ぶ）が、Issue #N に「前の PR #M で一部が済んだ。残り：…」とコメントし（残りは、PRの説明の受け入れ条件のうち未チェックの行 `- [ ]`。取れなければ「PR #M の説明を見て、残りを続ける」）、`ai:implement`・`ai:retry` を外して `ai:queue` に戻す（同じ Issue の続きを、次の実装AIがやる）。PRごとの印 `<!-- refs-merge-pr: #M -->` で二重には処理しない。同じ Issue で3回目の `Refs` のマージ（印が3個目）は、続けず `ai:stuck` で人間に回す（同じ所を回り続けないため）。『人間にお願いしたいこと』のPR（`park_issue_after_human_request_merge` が受け持つ）・`Closes` のPR・閉じた Issue では何もしない。見張り役は、`ai:implement` の Issue に紐づく（ブランチ `claude/issue-N-`）マージ済みのPRがあれば、`ai:retry` を付けずにこの関数で戻す（取りこぼしの拾い直し。印のあるPRは何もしないので、戻したあとの実装AIが止まったときは、いつもどおりやり直す）。実装AIには、「人間が別Issueを起こしてください」と書かず、残りを未チェックの行で書くよう伝えてある（`prompts/base.md`）
- 実装AIが「もう直っている（変更は要らない）」と確かめて終わった（ほかの Issue のPRで先に直った、など）：人間に回さず、AIが確かめた中身をコメントに残して Issue を閉じる（`open-pr.sh`、言い方は `ALREADY_FIXED_RE`）。まだ直っていなければ、開き直すと企画からもう一度進む
- もう一度レビューに回すとき（PRの説明だけを直した・修正AIが「指摘は誤り」か「前の対応で直し済み」と返した・レビューのやり直し）に、PRが main とコンフリクトしている：GitHub はコンフリクトしたPRでは pull_request のワークフローを動かさないので、`ai:review` を付け直してもレビューAIは起きない。先に修正AIにコンフリクトの解消を頼む（`request_review`。直す回数ではなく、コンフリクトの回数に数える。基準の画像だけならAIを呼ばずに解く。解消して push されると、CIのあとでレビューに回る）

**使用量の上限**：原因が使用量の上限と分かったとき（企画AI・実装AIの実行記録に「usage limit」などが出ているとき）は、回数を使わずに待つ。リセット時刻が読めれば、その1分後にやり直す。読めなければ60分あけてやり直す。待ちに入った最初の1回だけ、スマホに「使用量の上限で待っています」と通知する（通知の種類 `limit`）。上限が24時間以上続いたら、本物のエラーと同じに数えて、10回で `ai:stuck` にする。修正AI・レビューAIも、実行記録（成果物 `ai-result`。進行役が `EXECUTION_FILE` で渡す）から同じように見分ける。実行記録が無いときは、30分あけて、回数に数える。使用量の上限で止まったときは、途中に拒否された操作があっても、許可の不足として人間に回さず、上限として待つ（`handle_ai_failure`）。

- 実装AIが正常に終わったのに変更を残さず、実行記録に「拒否された操作」がある：拒否された操作と、AIが最後に言ったことをコメントに書き（これが、やり直す実装AIへの手がかりになる）、`ai:implement` を付け直して1回だけやり直す（`<!-- auto-perm-retry -->`。`open-pr.sh`）。やり直しても同じなら、足りない許可を書いて人間に回す。人間が `ai:stuck` を外して再開すると、また1回やり直せる
- 企画AIが「他の Issue・PR が終わらないと始められない」と判断した（`BLOCKED`）：人間に頼まず `ai:blocked` で待ち、待ち先が全部閉じたら見張り役が `ai:plan` に戻す
- 企画AI・実装AI・レビューAI・修正AIが、エラーで終わった。ただし、`ai:plan` が付け直されて新しい実行に置き換わった（取り消された）企画は、失敗として扱わない。企画のやり直し待ち（`ai:retry`）の Issue が、もう先へ進んでいれば（`ai:implement`・`ai:queue`・`ai:question`・`ai:mocks`・`ai:blocked`）、見張り役は印を外すだけでやり直さない（使用量の上限に当たったときなど。リセットされるまで待ちながらやり直す）
- 企画AIが、作業回数の上限（`--max-turns 30`）に届いて、結果（`plan-result.txt`）を書く前に終わった（コードの多いリポジトリでは、読むだけで届く。同じ上限でやり直しても同じ所で止まる）：同じジョブの中で1回だけ、上限を50回に増やしてやり直す（`claude-plan.yml` の「作業回数の上限に届いたか」。30分は待たない）。やり直しのAIには、2回目であること・仕様書は関係する節だけを読むこと・前回の途中の結果（書き直した本文・作った Issue）を二重にしないことを伝える。いつもの上限は30回のまま。増やしても届いたら、やり直さずに人間に回す（`after-plan.sh`。`PLAN_TURNS_RAISED`）。使用量の上限・ほかのエラーで終わったときは `ai:retry`
- 企画AIは正常に終わって（実行記録の結果が `success`）結果（`plan-result.txt`）も書いたのに、AIのアクションが失敗にした（手数が `--max-turns` を少し越えて終わると、アクションは「上限を越えた」として失敗にする。途中で拒否された操作があると、その分の手数で越えやすい）：清書は済んでいるので、失敗として扱わず、結果を使ってそのまま先へ進める（`after-plan.sh`。`ai_finished_ok`）。拒否された操作があっても、人間に回さない（agent-desk #447 は、これで「許可不足」として止まった）
- 実装AIが時間切れなどで終わり、失敗の知らせも無いまま45分以上動きが無い（`IDLE_IMPLEMENT_MIN`）。45分以上90分未満は、実装AIの実行が動いている・始まるのを待っている（`in_progress`・`queued`）間は、止まったとみなさない（審査役と直しを含めて75分まで動き、その間 Issue に何も書かれないことがあるため）。実行の一覧を読めなかったときも、この間の物は見ない。90分以上（`IDLE_IMPLEMENT_HARD_MIN`。実装のジョブの上限75分＋PRを作るジョブ5分より長い）は、ほかの Issue の実装が動いていても、一覧を読めなくても、止まったとみなす（`open-pr` が落ちた・実装が時間切れになった、など。どの Issue の実行かは見分けず、時間だけで判断する）。いつも別の実装が動いている並列の作業でも、止まった Issue が拾われる
- 見張り役が GitHub の API を読めなかったとき（一時的なエラーなど）は、空の結果を「正常」と読まない：Issue の更新時刻を読めない・空なら、その Issue はその回は飛ばす（企画・実装・画面案の止まりの判定。空のまま計算すると、今日の0時から動いていないことになる）。ラベルを読めなければ、その物には触らない（`has_label` は、付いている・付いていない・読めないを分ける。`ai:stuck`・`ai:skip` などの「付いていたら触らない」確かめは、読めなければ付いているものとして扱う。`has_label_or_unreadable`）。次の見張りが改めて見るので、通知は出さない
- 画面案（`ai:mocks`）のまま、動きが無い（見張り役の 2.5）：画面案は、AIが動くジョブ（`work`）のあとの後片付け（`publish`：画面案のコメントを書いて `ai:question` にする・案なしなら `ai:plan` にする）で次へ進む。`work` が時間切れ・取り消しになる、後片付けが途中で落ちると、`ai:mocks` が残ったまま、失敗の知らせも `ai:retry` も付かない。`ai:mocks` のまま120分（`IDLE_MOCKS_MIN`。画面案のジョブの時間の上限 100分より長い）何も起きなければ（ほかの画面案のジョブが動いていても待っていても、この時間は上限より長いので、止まったとみなす。どの Issue の実行かは見分けない）、見張り役がやり直し待ち（`ai:retry`）にし、30分以上あけて `ai:mocks` を付け直す（画面案が最初から動く。印 `<!-- auto-mocks-retry -->`）。やり直すのは、同じ画面案の回で1回だけ（Opus を長く動かすので、何度も回さない）。それでもまた止まったら、人間に回す（`ai:stuck`。外すと画面案をもう一度作る。案なしで進めるなら、`ai:mocks` を外して `ai:plan` を付ける）
- CIは終わっているのに、誰も先へ進めていない（見張り役の 3.4）：次の一手は、CI・レビューAI・修正AIが終わったときに進行役（`pipeline.yml`）が決める。その処理が途中で落ちた（APIの一時的なエラー・回数制限）・呼ばれなかった（CIや修正AIが時間切れで「取り消し」になると、進行役は動かない）ときは、ラベルも記録も残らず止まる。CIが終わっていて、待つ理由（`ai:stuck`・`ai:retry`・`visual:update`・レビューまで済んだ `ai:hold`）が無いのに45分（`IDLE_ORPHAN_MIN`）何も起きていなければ、見張り役が続きを動かす：CIが通っていればレビューへ、落ちていればAIに直させる（どちらも `after-ci.sh`）、取り消し・時間切れならCIを動かし直す、直す依頼に応答が無ければ同じ依頼をやり直し待ちにする。動かしたPRには印（`<!-- auto-nudge: 先頭コミット -->`）を残し、同じ先頭コミットでもう一度止まったら人間に回す。先頭コミットにCIの実行が1件も無い場合（イベントの取りこぼしなど。レビューが通っても `after-review.sh` が「CIがまだ」で終わり、印も通知も無く止まる）も、main とコンフリクトしていなければ、同じ45分で空のコミットを足してCIを動かし、そのコミットに印を付ける。そのコミットにもCIの実行が無いまま止まっていたら、人間に回す（コンフリクトしているPRは 3.2 が扱う）。配布のPR（`pipeline-sync/`）も見る：続きは配布の流れ（`after-ci.sh`。通っていれば main を取り込むかマージ、落ちていれば人間に回す）で動かし、同じ先頭コミットでもう一度止まったら人間に回す（印は同じ）。ただし、CIの実行が1件も無い配布のPRには空のコミットを足さない（次の配布で作り直される）。下書きのPRは見ない。fork からの他人のPR（head がこのリポジトリではないPR）には、見張り役は何もしない（ブランチへのpush・空コミット・修正の依頼をしない）。作者がオーナーでもパイプライン（App・bot）でもない Issue には、`ai:retry` のやり直しや `ai:plan` の付け直しをせず、`ai:skip` を付けて印を外す
- レビューAIの結果が出ないまま30分以上たった
- 外の障害（Ubuntu のミラーなど）：落ちた手順がブラウザ・依存を入れる所だけ（`NETWORK_CHECK_STEPS`）で、そのジョブのログ（`READ_TOKEN` で読む）に `Failed to fetch`・`ETIMEDOUT`・`Could not wait for server fd` などがあるときは、コードを直しても治らないので修正AIに頼まず（直す回数にも数えない）、落ちたジョブをすぐやり直す（コミットごとに2回まで。ワークフローの中で待たないので、5分・15分の間隔は置かない）。2回やり直しても同じなら `ai:stuck` で人間に回す。ログを読めないとき・言葉が無いとき・ほかの手順も落ちているときは、下の今まで通りの流れ。この判断は、撮り直し・パイプライン側のやり直しより前に行う
  - そもそも apt に行かない（#255）：見た目のテスト用のブラウザは `~/.cache/ms-playwright` を `actions/cache` に置き、足りない時だけ `--with-deps`。撮影の準備の日本語のフォント（`install-ja-fonts.sh`）は、`.deb` を `~/.cache/ja-fonts-apt`（`JA_FONTS_CACHE`）に置いて、`actions/cache/restore`・`save` で戻す・残す（キー `ja-fonts-apt-<OS>-v1`）。`/var/cache/apt/archives` は root の物で書き戻せず、ランナーの設定で入れた後に消されるため。置いた `.deb` は `apt-get install` がそのまま使い（apt の一覧のハッシュと合う物だけ）、戻すのも残すのもAIが動く前の段で行う
- パイプライン自体の確認（スクリプトのテスト・shellcheck・ワークフローの確認（actionlint）。名前は `pipeline-lib.sh` の `PIPELINE_CHECK_STEPS` で、`ci.yml` の手順の名前と食い違うとテストが落ちる）だけが落ちて、PRが `.github/` を触っていない：原因はPRの変更ではなく、AIは `.github/` を直せないので、AIに頼まない。落ちたジョブを、同じ先頭コミットで1回だけやり直し（実行環境の入れ替わりなどの一時的な揺れ）、それでも落ちたら人間に回す（`ai:stuck`。テンプレートの側で確かめる）。「パイプライン側のテスト＋見た目のテスト」だけが落ちたときも、同じく先に1回だけやり直す（通れば見た目だけの失敗として撮り直しへ。まだ落ちるなら、上の「見た目以外の失敗」の流れ）
- mainが進んでPRのブランチに取り込めない（コンフリクト）：AIに解消させる（直す回数ではなく、コンフリクトの回数に数える。`MAX_CONFLICT_FIX`＝3回まで。上の「人間に回る（止まる）とき」）。画像など中身を混ぜられないファイルは、AIが `git checkout --theirs -- パス`（main の側）か `--ours` で片方を取る。見た目のテストの基準の画像は main の側を取り、そのあと `visual:update` で撮り直す。
  - **基準の画像だけのコンフリクトは、AIを呼ばずにパイプラインが解く**（`resolve_baseline_conflict`。`request_conflict_fix_or_stop` が、AIに頼む前に試す。コンフリクトの解消を頼む所は全部この関数を通る：`after-ci.sh`・`after-mention.sh`・`pipeline-lib.sh` の `request_review` と `merge_or_handle`・`watchdog.sh` の 3.2・3.3・マージ待ち・`resume.sh`・出し直し `reissue_stale_fix`）。コンフリクトしているファイルは、merge base から PR の側と main の側の両方で変わったファイル（`compare` の2つの向きの重なり。本物のコンフリクトより広いので、迷えばAIに回る）とみなす。それが全部、基準の画像の置き場所（`pipeline.json` の `visual_baseline`。glob の文字列か配列。`**` は0個以上のフォルダ。無ければ `tests/visual/**/*.png`。判定は `only_baseline_images`）に入っていれば、main を取り込むマージのコミットを API で作り（PRの先頭の木に、main の側で変わったファイルを main の木の中身・モードのまま重ねる。消えた物は消す。画像は main の側になる）、PRのブランチを早送りで動かす（force しない）。そのあと、印 `<!-- auto-conflict-images: 先頭コミット -->` と `<!-- auto-visual-update -->` のコメントを書いて `visual:update` を付ける（今の自動の撮り直しと同じ流れ。撮り直しの回数「main を取り込んだ後で2回まで」は、このマージのあとから数える）。直す回数もコンフリクトの回数も使わない。画像以外が1つでも重なっている・一覧が300件で切れている・main の木が切れている・ブランチを動かせない（その間に別の push が入った）・fork と配布のPR・同じ先頭コミットでもう一度試した、のどれかなら、今までどおりAIに頼む。修正AIが変更なしで撮り直しを頼み、PRがまだ `dirty` のとき（`after-mention.sh`）も、先にこれを試す。撮り直しが動いている間（`visual:update` が付いている間）にCIが見た目のテストだけで落ちても、`after-ci.sh` は重ねて `visual:update` を付けない（付け直すと、動いている撮り直しが取り消される）CIのあと、レビューの間に別のPRが先にマージされ、マージの時点でコンフリクトになったときも同じ（`merge_or_handle`）。コンフリクト以外の理由でマージできなかったときは、やり直し待ち（`ai:retry`。種類 `merge`）にする（黙って止まらない。下の「CI 以外のチェックが通っていない」）。PRの先頭に CI が1つも動いていないままコンフリクトしているとき（コンフリクトがあると GitHub は CI を動かさないので、CI のあとの処理も呼ばれない。例：基準の画像の撮り直しを push している間に、別のPRが main に入った）は、見張り役が見つけて同じようにAIに解消させる（同じ先頭には1回だけ。配布のPRは除く）
- 「CI が通っているか」（`after-review.sh`）は、先頭コミットの CI のワークフロー（`name == "CI"`、PRの実行）の、`created_at` がいちばん新しい実行だけで決める（`ci_state`。`ci_failed_steps` と同じ読み方）。success なら次へ進み、実行が無い・読めない・終わっていない・success 以外なら、今までどおり「CIがまだ全部通っていない」でマージしない（読めなかったときを通ったと取り違えない）。CI 以外の GitHub Actions の check run（`visual-update.yml` の `shoot`・`commit` の失敗や取り消し、配り先が残した自分のワークフロー、古い CI の実行）は、マージを止めない（無視する。撮り直しの失敗はそれ自身が知らせる）
- CI 以外のチェックが通っていない（`handle_external_checks`）：CI（GitHub Actions）もレビューも通ったのに、外部のサービス（Vercel など、GitHub Actions 以外の App）が先頭コミットに付けたチェック（check run）が落ちている・終わっていないとき。終わっていないだけなら1分ほど待ち、それでも通っていなければ、チェックの名前・理由・見に行く先をPRに書いて（印 `<!-- external-checks: 先頭コミット -->`）、やり直し待ち（`ai:retry`、種類 `merge`）にする。待ちが明けたら、見張り役がAIを動かさずに、レビューのあとの処理（`after-review.sh`）のマージの判断だけをやり直す（通っていればそのままマージ。レビューはやり直さない）。同じ先頭コミットで2回（`EXTERNAL_CHECK_RETRIES`）確かめ直しても通らなければ、名前と理由を書いて人間に回す（人間が再開したら、数え直す）。コミットステータス（Vercel の「Deployment has failed」など）は、マージを止めない。ただし、GitHub がマージを断ったとき（保護ルールで必須のチェックが落ちている、など）は、落ちている check run・コミットステータスの名前と理由を同じように書いて、同じ流れに乗せる
- コンフリクトしていて CI が来ない PR（`mergeable_state: dirty`。GitHub はコンフリクトしたPRで CI を動かさないので、CI のあとの処理も呼ばれず、黙って止まる。agent-desk PR #482）は、2か所でコンフリクトの解消を頼む。どちらも文面は同じで、コンフリクトの回数に数え（直す回数には数えない）、同じ先頭コミットに直す依頼が出ていれば重ねて頼まない（`request_fix_or_stop`・`fix_requested_for`）：
  - 見張り役（`watchdog.sh` の 3.2）：先頭コミットに CI の実行が1件も無く、`dirty` のPR。CIの実行の一覧を読めなかったときは見ない。`mergeable` が `null`（`mergeable_state` が `unknown`。GitHub が計算中）のときは、頼まず・空のコミットも足さず、次の見張りまで待つ
  - 撮り直し・修正AIの push のあと（`after-mention.sh`）：push した後のPRが `dirty` なら、CI を待たず、すぐ頼む（レビューも動かないので `ai:review` は付けない）。`unknown` のときは頼まず、見張り役に任せる
  - 頼んだのに応答が無いまま止まったとき（修正AIが時間切れ・取り消しになった、変更なしで終わって `after-mention.sh` も動かなかった、など。CI が無いので 3.4 の `lost_fix` には来ない）：見張り役が、3.2 と、3.4 の中の人間のマージ待ち（`ai:hold`）の両方で見る（`handle_lost_conflict_request`）。同じ先頭コミットへの、いちばん新しい依頼から `IDLE_ORPHAN_MIN`（45分。修正AIの上限 30分より長い）たっても `dirty` のままで、このPRのブランチで Claude Mention（`claude-mention.yml`）の実行が動いても待ってもいなければ、`lost_fix` と同じに扱う。1回目は同じ依頼をやり直し待ち（種類 `mention`、印は `auto-fix-retry`）にし、やり直した依頼にも応答が無ければ `ai:stuck`＋通知で人間に回す。実行の一覧を読めないときは「動いている」とみなして待つ。依頼から45分たっていない間は、今までどおり何もしない
- 自動のマージを GitHub が断った（コンフリクト以外。落ちているチェックも見つからない）：やり直し待ち（種類 `merge`）にし、見張り役がAIを動かさずにマージだけをやり直す（レビューAIは動かさない）
- CIが「承認待ち」で止まった（空のコミットを足してCIを動かし直す）
- マージが GitHub の一時的なエラー（502 など）で失敗した：少し待って3回まで試す（`merge_pr`。ふつうのPRも、配布のPRも）
- `visual:update` が付いたまま10分たっても、撮り直しが動いていない（見張り役）：ラベルを外し、main とコンフリクトしていればAIに解消させる（コンフリクトの回数に数える。基準の画像だけならAIを呼ばずに解く）。コンフリクトが無ければ1回だけ付け直し、それでも動かなければ人間に回す
- レビューAIが、結果のコメント（`## Code review`）を書いたあとにエラーで終わった：書けた結果で進める（やり直すと30分待ったうえ、同じレビューをもう一度するため）。結果が書けていなければ、やり直し
- レビューAIが、エラーにならずに結果のコメントを書かずに終わった（一時的な不調）。2回までは自動でやり直し（`ai:retry`）、続くなら人間に回す。ただし、レビューのワークフロー自体（`.github/workflows/claude-review.yml`）を変えるPRでは、レビューAIは動けない（ワークフローが main と同じ内容でないと、AIのアクションは何もせず成功で終わる）ので、やり直さず、理由を書いてすぐ人間のマージ待ち（`ai:hold`）にする。逆に、PR は `claude-review.yml` を変えていないのに、先頭の版が main と違う（main 側でワークフローが変わったあと、枝が古いまま残っている）ときも、レビューAIは毎回飛ばされる（ログに `Skipping action due to workflow validation`）。この場合は、やり直しの回数に数えず、`update-branch` で main を取り込み、新しい先頭でCIとレビューをもう一度動かす（`after-review.sh`。コンフリクトで取り込めなければ、`request_fix_or_stop` でAIにコンフリクトの解消を頼む）。版の比べ方は、`contents` API の `sha`（PRの先頭と main）
- レビューの指摘がワークフローの所（`.github/workflows/`・`.github/actions/`。AIは push できない）だけを指している：修正AIに頼まず、すぐ `ai:stuck` にして「マネージャーが直してください」と指摘の場所（行への指摘は API の `path`、まとめは本文中のパス）を書く（`review_paths_kind`）。アプリのファイルと混ざっていれば修正AIに頼み、「ワークフローの所は直さず、PRにその旨を書く」と足す。パスが読み取れない指摘は今までどおり修正AIに頼む。修正AIが変更なしで終わったときも、指摘にワークフローの所が含まれていれば、理由を `unknown` ではなく「ワークフローの指摘が残っている」にして `ai:stuck` にする（`classify_no_change` の `workflow`）
- 見た目のテストだけが落ちていて、PRに「見た目を変えた（`visual:update`）」と書いてある（意図した変更なので、AIに直させず `visual:update` を付けて基準の画像を撮り直す。main を最後に取り込んだ後で2回まで（取り込むと基準の画像は main の側に戻るので、それより前の撮り直しは数えない。人間が `ai:stuck` を外して続きを頼んだ後も数え直す。`visual_update_count`）。意図していない崩れは、AIに直させる）。AIに直させるときは、落ちたCIの差分の画像（`visual-diff`）を先に取ってきて見せる（`fetch-visual-diff.sh`）。AIは画像を見て、頼まれた変更なら `visual:update` を頼み、崩れならコードを直す。修正AIがコードを変えずに終わり、AIの返事・この先頭コミットへのレビューの指摘のどちらかに撮り直しの依頼（`visual:update`、「基準の画像が古い」など）があるときも、進行役が `visual:update` を付けて撮り直す（CIが通っていて、レビューだけが指摘したときも。同じ数え方で2回まで、3回目は人間に回す）。見た目のテスト以外のチェックも落ちているときは、すぐ人間に回さず、順に進める（`after-ci.sh`・`after-mention.sh`）：①落ちたジョブを、同じ先頭コミットで1回だけやり直す（`rerun_failed_ci_once`。印は `PIPELINE_TEST_MARK` に「コミット <sha>」を添えて数える）②やり直しても見た目以外が落ちるなら、修正AIに「見た目以外の失敗だけを直して。画像の差は気にしなくていい（あとで撮り直す）」と頼む（直す回数に数える。`request_fix_or_stop`。印 `<!-- auto-fix-nonvisual -->`。同じ依頼で変更なしが続けば人間に回す）③落ちているのがパイプライン側のテスト（`PIPELINE_CHECK_STEPS`）だけで、PRが `.github/` を触っていないときは、修正AIが直せないので人間に回し、文に「PRと関係ない所（パイプライン側）のテストが落ちている」と書き、テンプレートに直すIssueを作る（同じ題名の開いたIssueがあれば作らずコメントで足す。`report_pipeline_test_to_template`。テンプレートが分からない・作れないときは、文に「Issueを作ってください」と書く）④見た目以外が通れば、CIが見た目のテストだけの失敗になり、今までどおり撮り直しへ進む。撮り直しのコミットが入ると、CI とレビューが最初から走り直す（レビューのあとの処理は、先頭コミットより後のレビュー結果だけを見るので、古い画像へのレビューは引きずらない）。撮り直した画像はPRに入るので、レビューAIは前（PRの元）と後（PRの先頭）の画像を開いて見比べ、Issueどおりの変化か・崩れが無いかを確かめる（`claude-review.yml` の「見た目の画像の前と後を用意する」。1回に12組まで）。基準の画像はCIの環境で撮るので、同じ環境なら毎回同じ絵になる。見た目のテストの閾値（Playwright の `maxDiffPixelRatio` など）は小さくしておく（大きいと、小さい見た目の変更が通ってしまい、古い基準の画像が残る）

修正AIと撮り直しを同時に動かさない（agent-desk PR #478。順番は、修正 → 撮り直し → レビュー）：修正AIと基準の画像の撮り直し（`visual-update.yml`）は、どちらもPRのブランチに push する。同時に動くと、先に入った push のせいで、後の修正AIは「PR #N was updated after the trigger … Mention Claude again」とだけ書いて何もせずに終わる（依頼のコメントのあとにPRが更新されていると、AIのアクションは動かない）。
- 同じ先頭コミットに、まだ終わっていない直す依頼があれば、どこから頼んでも重ねて頼まない（`request_fix_or_stop` が `fix_requested_for` で確かめる。CI・レビュー・撮り直しの失敗（`visual-update.yml`）・見張り役のどれも。回数にも数えない）。「終わった」は、依頼のあとに修正AIの `Claude finished` の返事がある・修正AIが「PRが更新されたので動かない」と返した・人間が `ai:stuck` を外した、のどれか。修正AIのあとの処理（`after-mention.sh`）からの依頼は、動いていた修正AIがもう終わっているので確かめない
- 見た目のテストだけが落ちても、その先頭コミットに直す依頼が出ていれば、撮り直しを始めない（`after-ci.sh`。直した push のあとの CI で、もう一度決める。撮り直しの回数にも数えない）。レビューの指摘がもう出ている（CIと同時に動いて先に終わった。直す依頼はまだ）ときも、撮り直しは始めず、その場で「レビューの指摘を直す。見た目のテストは、画像でない確かめが落ちていれば直し、画像の差だけなら何もしない」と頼む（`review_has_findings`。あとから動く `after-review.sh` は重ねて頼まない）
- レビューに指摘があっても、撮り直し（`visual:update` のラベルが付いている間）が動いていれば、直すよう頼まない（`after-review.sh`）。続きは撮り直しの側が動かす：画像が変われば push されて CI とレビューがもう一度動き、変わらなければレビューに回し直し、失敗すれば直すよう頼む
- それでも修正AIが「PRが更新されたので動かない」で終わったとき（人間の push と重なった、など）：その依頼は直す回数に数えず（`count_auto_fix`）、`after-mention.sh` が同じ文の依頼を最新のコミットで出し直す（`reissue_stale_fix`。同じ「n/3」・同じモデルのまま。「直してpushした」とは扱わない）。いまの先頭コミットに別の依頼がもう出ていれば出し直さない。人間が `ai:stuck` を外した後で4回続いたら、何かがブランチを動かし続けているので人間に回す（`MAX_STALE_FIX`＝3回まで出し直す）

修正AI（`@claude 直して`）が正常に終わったのに変更が無いときは、`after-mention.sh` が理由を分けて動く（`classify_no_change`。AIの返事のキーワード・レビューの指摘・実行記録を、上から順に見る。PRの説明は見ない）：
- **人間のラベル作業が要る**（基準の画像の撮り直し）：上のとおり、進行役が `visual:update` を付ける（2回まで）。ただし、main とのコンフリクトが残っているPRでは付けない（コンフリクトがあると、GitHub は撮り直しもCIも動かさないので、付けても何も起きない）。拒否された操作があれば、解消のしかた（`git checkout --theirs -- パス`）を書いて1回だけ出し直し、無ければ理由を書いて人間に回す。見た目のテスト以外も落ちているときは、止まらずに「やり直し→修正AI→撮り直し」の順で進める（上の撮り直しの説明）。人間に回るのは、撮り直しを2回しても、まだ頼まれたとき、パイプライン側のテストが本当に壊れているとき（テンプレートにIssueができる）だけ
- **ツールの許可が拒否された**（実行記録の拒否、または AIが「許可されていない」と報告）：拒否された操作をそのままの形でコメントに書き、同じ依頼を1回だけ出し直す（`<!-- auto-perm-retry -->`。直す回数には数えない。人間が `ai:stuck` を外して再開すると、また1回やり直せる）。2回目も拒否されたら、足りない許可の候補を書いて人間に回す（`ai:stuck`。同じ不足が2回で、直すためのIssueを自動で作る）
- **指摘が間違いと返した**（「指摘は誤り」「直す必要はない」など。理由はAIのコメントに残る）：`ai:review` を付け直して、もう一度レビューに回す。同じ指摘が続けば、レビューのたびに直す依頼が数えられ、直す回数の上限で人間に回る。CIが落ちたままなら先へ進めないので人間に回す
- **分類できない**（質問した、など）：やり直さず人間に回す（`ai:stuck`）

## 安全のしくみ

**要点**：合否を決めるのはCI。AIには強い鍵を渡さず、仕組みそのもの（`.github/`・`CLAUDE.md` など）はAIの判断だけで書き換わらない。他人の Issue・コメントでは動かない。

- **オーナー以外が作った Issue は、自動で動かさない**：公開リポジトリでは誰でも Issue を作れる。受付（`intake.sh`）は、オーナーとこのパイプラインのワークフロー（`github-actions[bot]`・`claude[bot]`。`trusted_author`）以外が作った Issue に `ai:skip` を付け、雛形（メモ）で付いた `ai:plan` などの作業のラベルを外す。パイプラインの App がラベルを付けて作った Issue（使ってみる役・監査役の `ai:found`）は、そのまま進める。`ai:skip` が付いている間は、企画・実装のワークフローはラベルが付け直されても始まらず（ジョブの条件）、企画のあとの処理（`after-plan.sh`）も、見張り役のやり直し・止まりの検知も動かない。受付が動かなかったときの保険（見張り役の 3.5）も、オーナー以外の Issue は企画に回さず `ai:skip` で止める。オーナーが `ai:skip` を外すと、企画に回る（雛形の `ai:plan` を残すと、自動のやり直しがパイプラインの鍵で付け直して、他人の Issue を企画・実装してしまうため）
- **`@claude` を呼べるのは、人間と、このパイプラインの App だけ**：修正AI（`claude-mention.yml`）は、コメントに `@claude` があると動き、PRのブランチに push できる。公開リポジトリでは誰でも（どのボットでも）コメントできるので、ジョブの条件で絞る。呼べるのは、（1）人間のオーナー・メンバー・共同作業者と、（2）このパイプラインの App が書いたコメントだけ。App は名前（`〜[bot]`）ではなく、コメントに付く「どの App が書いたか」の番号（`performed_via_github_app.id`）が、変数 `PIPELINE_APP_ID`（鍵を作るのに使う番号）と同じかで見分ける。ほかのボット（あとから入れた別の App・dependabot など）と AI自身（`claude[bot]`）は呼べない。`PIPELINE_APP_ID` が空のリポジトリ（`PIPELINE_TOKEN` で動かしている）では、進行役のコメントはオーナーの名前で付くので（1）に入り、ボットは1つも呼べない。ボットは、コードの行へのコメントでも呼べない（どの App が書いたかがイベントに無く、作業フォルダが最初からPRのコードになるため。進行役の直す依頼は、いつもPRへの普通のコメント）。AIのアクションに渡す許可（`allowed_bots`）も同じ決まりで作る。トークンを持って動く道具（`pr-trust.sh`・`fetch-visual-diff.sh` など）は、作業フォルダの版ではなく main から取った版を動かす（`test-workflows.sh` が、誰のどのコメントで動くかを場面ごとに確かめる）
- **AIにコメントを渡すときは、信頼できる書き手の物だけ**：公開リポジトリでは、他人がオーナーの Issue・PR にコメントできる。`gh issue view --comments` や `gh pr view --comments` で全部読ませると、他人の指示が AI に届く（企画AIは Issue を作れ、その Issue は `github-actions[bot]` 作として実装まで進むため、他人の文章が実装まで届く道になる）。そこで AI が動く前に `trusted-comments.sh <番号>` で、タイトル・本文・コメント（書いた人と日時つき）のファイルを作って渡し、AI には `--comments` を使わせない。残すのは、（1）`author_association` が `OWNER`・`MEMBER`・`COLLABORATOR` の人、（2）`github-actions[bot]`・`claude[bot]`、（3）`performed_via_github_app.id` が変数 `PIPELINE_APP_ID` と同じ App（空なら（3）は無し）。上の「`@claude` を呼べるのは…」と同じ決まり。ほかのコメントは中身も名前も出さず「（信頼できない人のコメント N 件は省略）」と件数だけ書き、本文を書いた人が信頼できないときは、タイトルと本文も出さない。読めなかったときは、スクリプトは何も出さず失敗で終わる（黙って全部は渡さない）。企画・レビュー・画面案のワークフローは、そのとき「読めなかった」とだけ書いたファイルを渡し、AI は `--comments` なしで本文だけを読んで続ける（#196）。判定は純粋な関数（`trusted_render`）で、`gh` を呼ぶ部分と分けてある。トークンを持って動く道具と同じく、main から取った版を動かす
- **閉じた Issue では進めない**：企画・実装・画面案は、開いている Issue でだけ始まる。作業中に Issue が閉じられたら、企画のあと（`after-plan.sh`）は清書の結果を使わず、実装のあと（`open-pr.sh`）はPRを作らない（同じ作業のPRが2つできないように）
- レビューAIは、画面のファイルが変わったPRでは web-design-guidelines（`.claude/skills/web-design-guidelines/guidelines.md`）も当て、使う人が実際に困る物（キーボードで操作できない・フォーカスが見えない・ラベルが無い・`prefers-reduced-motion` を無視・ズームの禁止・長い文字や空で崩れる・取り消せない削除など）だけを指摘する。`docs/design.md` が決めていることは、そちらが正しい
- レビューAIは、確かめを弱めた変更も見る：テストを消した・飛ばした・期待する値を実装に合わせて書き換えた、`package.json` の `scripts` やリント・型チェックの設定をゆるめた、`any`・`@ts-ignore`・`eslint-disable` でエラーを消した。Issue が頼んでいなければ指摘する（合否を決めるのはCIなので、CIの中身を変えて通したPRは、通ったことにならない）。入力から出力が決まるロジックを足した・変えたのにテストが無いときも指摘する
- レビューAIは普段 sonnet。追加＋削除が300行を超える変更と、ログイン・トークン・秘密・権限・依存（`package.json`）・ワークフローを触る変更は opus でレビューする（`claude-review.yml` の「レビューのモデルを決める」）
- AIが動くジョブには `PIPELINE_TOKEN` を渡さない。企画・実装のあとの処理（次へ進める・PRを作る）は別のジョブで、main から取り直したスクリプトを動かす。AIが作業フォルダのスクリプトを書き換えても、強いトークンでは動かない（AIの結果は、実行記録と `plan-result.txt` をデータとして受け渡すだけ）
- パイプラインの更新を配る（`sync.yml`）のは、テンプレートの main でCIが通った版だけ。CIが通ってから15分待ち（変数 `SYNC_DELAY_MIN` で変えられる。手で動かしたときは待たない）、その間に main がまた更新されたら新しい方だけを配る（続けてマージしても、配り先のPRは1つで済む）。配り先は、このテンプレートから作られ、パイプラインの鍵（App）が見えるリポジトリ（自動。新しいアプリを作っても書き足さなくてよい）と、`.github/sync-targets` に書いた物（テンプレートより前からあるリポジトリなど）。配りたくない物は `.github/sync-targets` に `!owner/repo` と書く（`sync-targets.sh`）。リポジトリの一覧を読めないとき（鍵が無い・期限切れ）は、書いた物だけに黙って配らず、失敗で終わる。配るときは配り先の `.github/` をテンプレートの物で置き換える（テンプレートに無いファイルは消える）。配り先で自分で足したワークフローなどを残したいときは、配り先の `.github/sync-keep` に、そのファイルの名前を1行に1つ書く（例：`workflows/my-job.yml`）。配り先の main には直接入れず、`pipeline-sync/<sha>` のPRを作る。配り先のCIが通ったら、進行役がレビューなしでマージする（落ちたら `ai:stuck` で人間に回す。main が先に進んでいれば先に取り込み、取り込めなかったときも、黙らず `ai:stuck`・コメント・通知で人間に回す。AIが作ったPRや、印の無いPRはこの扱いにしない）。前の配布のPRの一覧を読めない配り先は、警告を出してそのアプリだけ飛ばし、後ろのアプリには配る（全体は失敗で終わる）。配布のPRの本文には、元のリポジトリと sha の印 `<!-- pipeline-sync-src: owner/repo@sha -->` を入れる（印の無い古いPRは、ブランチ名 `pipeline-sync/<sha>` から sha だけ読む）。同じ配布が複数のアプリで落ちたとき（テンプレートのテストの不具合など、原因が1つのとき）、「パイプラインの更新が入りません」の通知は最初の1件だけにする（`sync-failure-report.sh`）。テンプレートに、タイトル `配布 <sha> が配り先で落ちています` の Issue（ラベルなし。「テンプレートの main のCIは通っているが、配り先で落ちた」という説明）を1つ作り、これが先にあれば通知を送らず、その Issue に「`owner/app` PR #n：CIが落ちました」を1行コメントする（同時に作って重複したら、いちばん番号が小さい Issue をまとめ先にする）。PRへのコメントと `ai:stuck` は今までどおり付く。まとめ先の Issue は、人間が閉じるまで開いたままにする。テンプレートの Issue を読めない・作れないとき（鍵に権限が無い・印が無い）は、通知は今までどおり送る（消えるよりは重複する方へ倒す）。「マージできなかった」通知は、まとめない
- `.github/`・`.claude/`・`docs/pipeline.md`・`docs/pipeline-setup.md`・CLAUDE.md・AGENTS.md・`pipeline.json` を変えるPRは、CIとレビューが通っても自動でマージしない（マージを人間に任せて通知する）。仕組みそのものが、AIの判断だけで書き換わらないようにするため。普通のIssueは全自動
- 合否を決めるのはCI。AIの「できました」は信じない
- 進行役（pipeline.yml）は `workflow_run` で main にある版が動くので、PRの中身で判断を書き換えられない
- AIは `.github/`・`docs/pipeline.md`・`CLAUDE.md`・依存パッケージを触らない。`docs/spec.md`・`docs/design.md` は、見た目や挙動を決めるIssueのとき、実装の前に更新して同じPRに入れる（CLAUDE.md）。レビューAIが、書いた内容がIssueの範囲かを見る
- レビューAIは毎回、前の指摘が直ったかも含めて見直し、必ず「## Code review」で始まるまとめを残す（進行役はこれで判断する）
- 自動の修正は3回まで（最後の1回は opus）、自動のやり直しは10回まで。無限に回らない
- AI（claude[bot]）のpushでCIが「承認待ち」になったら、進行役がオーナーのトークンで空のコミットを足してCIを動かし直す（PRが main とコンフリクト＝`dirty` でCIが0件のときは足さない。空のコミットでは動かず、先頭が変わって依頼の sha と食い違うため。代わりにコンフリクトの解消を頼む。`after-mention.sh`・`resume.sh`・見張り役 3.2）
- ai-dev-template 自身は、AIが `.github/scripts/`（テストを含む）・`docs/pipeline.md`・README だけを直すPRなら、CI（`script-tests`・`shellcheck`）とレビューが通れば自動でマージされる。印は main の `CLAUDE.md` の `pipeline-self-edit: auto` で、進行役は main の物を見るので、PRで印を足してもすり抜けられない。それ以外のパイプラインの物（`.github/` の `scripts/` 以外すべて（`workflows/`・`actions/`・`factory/`・`sync-targets` など）・`.claude/`・`docs/pipeline-setup.md`・`CLAUDE.md`・`AGENTS.md`・`pipeline.json`）は、どのリポジトリでもAIが無人で書き換えない（人間側のClaudeが行い、マージは `ai:hold`）
- 公開後に壊れていたら、Vercelの画面から前の版にすぐ戻せる

## コミットのステータス「AIレビュー」（人間もマージできないようにする）

人間のマージ待ち（`ai:hold`）のPRは、PRができた時点で画面からマージできてしまう。レビューが始まる前・指摘を直している間にマージしないよう、レビューの結果を先頭コミットのステータス（context `AIレビュー`）として付け、main の保護で必須にできるようにする。既存のチェック `review` は、指摘があってもジョブとしては成功なので、必須にしても止められない。

**意味**：`pending`＝レビュー前・中、`success`＝指摘なし／レビューを通さない決まりのPR、`failure`＝指摘あり。進行役（main の版が動く `after-review.sh`・`after-ci.sh`）が付けるのは小さな部品 `review-status.sh <sha> <pending|success|failure> "<説明（140字まで）>"`（環境変数 `STATUS_TOKEN`＝ワークフローのトークン。`statuses: write` が要る）。`STATUS_TOKEN` が無い・書けないときは警告を出すだけで失敗にしない（権限が入るまでは今までどおり動く）。

| 場面 | 付くもの | 付ける所 |
| --- | --- | --- |
| レビューを始めた | `pending`（AIがレビュー中です） | `claude-review.yml` の最初のステップ（PRのスクリプトは呼ばず、`gh api` を直接書く。PRで書き換えられて `success` を付けられるのを防ぐ） |
| 指摘なし | `success`（指摘なし） | `after-review.sh`（CIを確かめる前） |
| 指摘あり | `failure`（指摘があります。AIが直しています） | `after-review.sh`（直すよう依頼する前） |
| 画像など文字で読めない変更だけ | `success`（理由つき） | `after-review.sh` |
| `claude-review.yml` を変えるPR（レビューAIが動けない） | `success`（人間が確かめてください） | `after-review.sh`（`ai:hold` を付ける所） |
| 配布のPR（`pipeline-sync/*`） | `success`（レビューは通さない。CIで決める） | `after-ci.sh`（マージの判断の前） |
| レビューAIがエラーで止まって自動でやり直す間 | 何も付けない（`pending` のまま） | 付け直しは、次のレビューの開始で行う |

**main の保護で必須にする手順**（設定するのは人間またはマネージャー。Administration の権限が要るので、パイプラインの鍵には持たせない。Doctor は「未設定」を知らせるだけで、設定はしない）：Settings → Branches → main の規則 →「Require status checks to pass」の検索欄で `AIレビュー` を選ぶ（承認は0人のまま）。ワークフロー側で `statuses: write` が入り、一度ステータスが付いたあとでないと、検索欄に出ない。PRができてからレビューが始まるまでの短い間はステータスが無いが、必須にしていれば、無い間もマージはできない。

## 読む量を減らす（Issue の「読む所」）

仕様書（`docs/spec.md`）とデザイン仕様（`docs/design.md`）は、Issueのたびに増える。AIが毎回全部を読むと、使用量の上限に早く当たる。そこで、いちど全部を読む企画AIが、清書のときに Issue の本文に `### 読む所` を書く（ファイルごとに、関係する節の見出し。見た目に触る作業なら、デザイン仕様の全体に効く決まりの節も。関係するコードのファイルも）。

- 実装AI・修正AIは、「読む所」があれば、仕様書を最初から全部は読まず、Grep で見出しを探して、その節だけを Read で読む。足りなければ追加で読む。「読む所」が無い Issue では、全部読む
- 行番号は書かない（順番待ちの間に、ほかの作業で変わるため）。仕様書が無い・短い（200行より短い）リポジトリでは、企画AIは「読む所」を書かない
- レビューAIは変えない（必要な所を自分で読む）
- 効いているかは、`ai-report.sh` が実行ごとに出す「使った量」（入力・キャッシュから・出力のトークン）で比べる

## Issue に貼った画像を、企画AI・実装AIに見せる

企画AI（`claude-plan.yml`）・実装AI（`claude-implement.yml`）の前に、`issue-images-prompt.sh` が Issue の本文の画像（`![..](https://…)`・`<img src="https://…">`）を取ってきて置く（企画は `issue-images/`、実装は `.shots/issue/`。コミットしない）。AIはネットに出ずに `Read` で見る。取るのは `fetch-issue-images.sh`（工場のデザイン担当と同じ。10枚まで・1枚10MBまで・JPEG・PNG・WebP・GIF だけ）。

- このリポジトリのファイルの画像（agent-desk が `issue-images` ブランチに置くスクショ。`github.com/<o>/<r>/raw/<ref>/<path>`・`raw.githubusercontent.com/…`）は Contents API で取る。非公開のリポジトリでも見られ、鍵は api.github.com にだけ送る。ほかの github.com の画像は鍵を付けて、それ以外のサイトは鍵なしで取る
- AIへの指示には、枚数と置き場所だけを足す（URL や本文の文字は混ぜない）。企画AIには、清書した本文にも画像の行を残すよう頼む（実装AIも同じ画像を見るため）
- 取れなかった画像があっても止めない（取れなかった枚数を伝える）。画像が無ければ何も足さない

## 指示を部品で組む（`compose-prompt.sh`）

実装AI・修正AI（mention）に渡す指示（`--append-system-prompt`）は、部品に分けて `.github/scripts/prompts/` に1ファイル1部品で置く。`.github/scripts/compose-prompt.sh` が、要る部品だけを順に連結して標準出力に出す。見た目のテストが無いリポジトリに基準画像の注意を読ませない、などで読む量とぶれを減らす。企画AI・レビューAIの指示は対象外。

| 部品 | 中身 | 入れるとき |
|---|---|---|
| `base.md` | コマンドは1つずつ・Read/Grep/Glob を使う・`.github/` は変えない | いつも |
| `read-sections.md` | Issue の「読む所」の節だけ読む | `--docs`（`docs/spec.md` が200行以上） |
| `merge-main.md` | push の前に main を取り込む・コンフリクトの解消 | いつも |
| `visual-tests.md` | 基準画像の扱い・`visual:update` ラベル・`test:visual` の動かし方 | `--visual-tests` |
| `visual-diff.md` | `.visual-diff/` の見方 | mention かつ `--visual-tests` |
| `pr-body.md` | PR の本文の直し方（`.pr-body.md`） | mention |

- 使い方：`bash .github/scripts/compose-prompt.sh --mode implement|mention [--visual-tests] [--docs]`。`--auto` を付けると、作業フォルダから自分で判定する（見た目のテスト＝`package.json` の `test:visual` か `pipeline.json` の `checks` にある。長い仕様書＝`docs/spec.md` が200行以上。企画AIの「短い」と同じ基準）
- 部品の文は、元のワークフローの指示をそのまま分けたもの（意味は変えない）。出し分けは mode と、リポジトリの条件だけ（Issue の種類では出し分けない）
- 選び方は `tests/test-compose-prompt.sh` で確かめる
- ワークフローは、AIを呼ぶ前の「AIへの指示を組む」の手順（`id: prompt`）でスクリプトを動かし、改行と `"` を除いた1行を `steps.prompt.outputs.text` に出して、`--append-system-prompt \"${{ steps.prompt.outputs.text }}…\"` で渡す（`claude_args` の中では `$(...)` が動かないため）。`claude-implement.yml` は Issue がきっかけで作業フォルダが main なので、そのまま `.github/scripts/compose-prompt.sh --mode implement --auto`。実装AIと審査後の直し役の2か所で同じ指示を使い、末尾の `${{ steps.shots.outputs.prompt }}${{ steps.target.outputs.prompt }}` は後ろに残す。`claude-mention.yml` は作業フォルダがPRの中身なので、`compose-prompt.sh` と `prompts/` を main の版から取ってきて（「道具を main から取ってくる」）`--mode mention --auto` で動かす（判定は作業フォルダで行う）

## AIの許可（`--allowedTools`）

各AIが使ってよい操作は、ワークフローの `--allowedTools` に書いてある。AIは、ここに無い操作をしようとすると拒否されて止まる。次の表が一覧（`.github/scripts/tests/test-permissions.sh` が、ワークフローと表が食い違っていないか確かめる）。

**ボットが作ったPRでは、許可していても拒否されるコマンドがある**（`claude-code-action` の `restrict_untrusted_prs`。既定で有効）。PRの作者に書き込み権限が確認できないとき、パッケージマネージャー・テスト・インタプリタ・シェルなど「PRのコードを動かすコマンド」（`npm`・`npx`・`node`・`bash` など）は、`--allowedTools` に入っていても拒否される。ボットは、`allowed_bots` に入っていても必ずこの扱いになる。このパイプラインのPRは、パイプラインの App（ボット）が作るので、何もしないと修正AIは確認コマンドを1つも動かせない（「npm が許可されなかった」と報告して、確かめないまま push する）。

そこで `claude-mention.yml` は、AIの前に `.github/scripts/pr-trust.sh` で次を全部確かめ、満たすときだけ `restrict_untrusted_prs: false` にする。それ以外のPR（fork・`claude/` ではないブランチ・閉じたPR・読めないとき）は、既定のまま拒否させる。

- PRのブランチが、このリポジトリの中にある（fork ではない。このリポジトリに push できるのは、書き込み権限のある人と App だけ）
- ブランチ名が `claude/` で始まる（実装AIが、このリポジトリのワークフローの中で作ったブランチ）
- PRが開いている

AIのアクションは作業フォルダをPRのブランチに切り替えるので、AIのあとの工程は、作業フォルダのスクリプトを動かさない（AIの前に、main の版を API で `$RUNNER_TEMP/pipeline-tools/` に取ってきて、それを動かす。`pr-trust.sh` も同じ（PRが書き換えた版に判断させない）。`tests/test-workflows.sh` が確かめる）。実装AI・企画AIは Issue で動くので、この拒否は掛からない。レビューAIは `gh` と読むだけなので影響しない。

許可が足りなくて止まったときは、次のようになる。

- 企画AI・実装AIがエラーで終わったときは、実行記録から拒否された操作を読み取り、「足りない許可：`Bash(git merge:*)`」のように、通知とコメントに書いて人間に回す（やり直しても直らないので、自動のやり直しはしない）。実装AIが正常に終わったのに変更が無いときは、拒否された操作を手がかりに書いて1回だけやり直す（上の「自動でやり直す」）
- 修正AIは、AIのコメントに「許可されていない」などと書かれていれば、その行と、出てくるコマンドから足りない許可の候補を書いて人間に回す
- 開けない操作の一覧：`Bash(rm:*)`、`Bash(sed:*)`、`Bash(curl:*)`、`Bash(git push --force:*)`、`Bash(git rebase:*)`、`Bash(gh pr merge:*)`（方針として許可しない物。`pipeline-lib.sh` の `PERM_NEVER_OPEN` と同じ一覧で、食い違うと `tests/test-permissions.sh` が落ちる）。AIがこれを試して止まったときは、止まった理由に「足りない許可」ではなく「開けない操作を試した（AIへの指示を直す所）」と書く（一覧に無い物が混じるときは、その物だけを「足りない許可」に書く）。記録のコメントは残すが、2回目になっても直すIssueは作らない（オーナーが押す物は無く、「あなたの番」のノイズになるため）
- 開けない操作ではない物の不足が2回起きたら、直すIssue（`AIの許可が足りない：…`）を、アプリではなく**テンプレート**に1つにまとめて作る（ラベル `audit`。マネージャーが `--allowedTools` と上の表を直す）。同じ題名の開いたIssueがあれば作らず、`<アプリ>#<番号>` をコメントで足す（題名が同じ物のうち最小の番号がまとめ先。「配布の失敗のまとめ」と同じ形）。テンプレートの名前は、環境変数 `PIPELINE_TEMPLATE_REPO`、無ければ最近の配布PRの印（`pipeline-sync-src: owner/repo@sha`）から読む。リポジトリ自身がテンプレートなら、そこに作る。`audit` ラベルが無くても、ラベルなしで作る
- テンプレートの名前が分からない・Issueを読めない／作れない（鍵が届かない）ときだけ、今までどおりアプリに `AIの許可が足りない：…` を作る。このときは `ai:skip` に加えて `pipeline` ラベルを付け、本文の頭に `<!-- pipeline-maintenance -->` を入れる（アプリの管理画面が「オーナーの番ではない」と見分ける印）
- 回数の記録は、閉じたままの「AIの許可の不足（自動の記録）」Issueのコメントに残る。記録Issueが重なって作られていたら、いちばん番号が小さい物を正とし、回数は見つかった全部のコメントを合わせて数える（余分な物は閉じたまま残す）
- 判断：`npm run lint` など確認コマンドの不足は、許可の表に足さず、アプリの `pipeline.json` の `checks` に入れて直す。テスト1本（`npm run test -- x`）は、確認コマンドを狭めるだけで害が小さいので、`--allowedTools` に足す案とする（ワークフローの変更なので、マネージャーが行う）

### 撮って見て直す

文字だけで画面を作ると、行をまたいで揃うはずの列のずれ・重なり・何も無い帯・弱い主役に、誰も気づけない（工場で作った最初の2つのサービスで起きた）。そこで、画面を作るAIは**自分で撮って見る**。

- 撮るのは `.github/scripts/shot.mjs`（依存なし。Chrome の操作は `.github/scripts/lib/cdp.mjs`（taste-skill から写した物、MIT）で、ubuntu-latest に入っている Chrome で撮る。Node 22 以上）。`--serve` でビルド済みのアプリを立ち上げてパス（`/` など）を撮るか、URL（実在のサイト）か HTML のファイルを撮る。幅は 390・1440・1920。`--scrolls N` で1画面ずつスクロールしながら N 枚撮る（スクロールで出てくる物・動きの途中が見える）。`--scale 2 --format webp` でサイトに載せる用の高精細で軽い画像にする。`--links` でページにあるリンクを出す（ギャラリーの一覧から、載っているサイトを拾う）。押す・入力する・localStorage にデータを入れるなどの操作をしてから撮る場面は `--steps` の JSON で書く（使い方はファイルの先頭）
- **実装AI**（`claude-implement.yml`）：画面のあるアプリ（package.json に `start` がある Node のアプリ）では、確認コマンドが通ったあと `npm run build` → `node .github/scripts/shot.mjs --serve /` で撮り、画像を全部見て、`docs/design-ref/` の目標の絵があれば見比べ、目立つ問題の上位3つを直して撮り直す（最大3回）。撮った画像は `.shots/` にでき、コミットされない（`.git/info/exclude`）。そのあと、**別のAI（審査役）**が、ワークフローが撮り直した画像（下へスクロールした続きも）と目標の絵だけを見て答え（コードは見ない）、合格（下の「デザインの仕組み」。今あるアプリへの変更は、足した所が `docs/design.md` の「このサービスらしさ」に沿っているか・崩れ・スマホ・足した所の型と地味さ）に届かなければ、指摘をつけて実装AIにもう1回だけ直させる。結果はPRの本文に入る。そのぶん時間の上限を 75 分にしている
- **デザイン担当**（工場）：実在の良いサイトを撮って参考にしてから、本物の画面を作り、撮って実例と見比べて直す（`docs/factory.md`）

## デザインの仕組み（考え → 関門 → 審査）

工場の画面は、ふだんは1案だけ作る（#193 の比べ直しで、2案にすると AI の使用量がほぼ2倍なのに点の差は 0.5 だった）。変数 `FACTORY_DESIGN_VARIANTS`（1〜3）を入れると、方向の違う案を同時に作って選ぶ（#118・#121。ゲーム・相談で見た目を決めた物は、変数があっても1案）。そのとき design ジョブが案ごとに並んで「作る → 確認 → 関門・審査 → 直し」まで行い、design-pick が `design-judge.py pick` で合格した中の最高点（無ければ最高点）を選んで build に渡す。時間は1案ぶん、AIの使用量は案の数ぶん。結果のコメントに全部の案の点が載る。

禁止の決まりを足し続けると、画面は無難で地味になる（11月2日）。決まりを外すと、AIの平均になる（11月16日。クリーム色に朱・等幅の数字・罫線だらけ、白い角丸の箱にインディゴ）。どちらも、**その題材にしか無い物が画面に無い**のが原因で、それを作ったAI自身は見抜けない。そこで、見た目を作る所は全部、次の3つを通す。特定の系統（雑誌風・ミニマルなど）には寄せない。どの系統でも、題材だけの考えが絵に出ていて、やり切っていれば通る。

| 段 | 誰が | 何をするか | どこに書いてあるか |
| --- | --- | --- | --- |
| 1. 考え | 作るAI（Opus） | 色や文字を選ぶ前に、**設計メモ**（`concept.md`）を書く：題材の持ち物を 8〜12 個 → 考え（「この画面では、〇〇が〇〇になる」。競合の名前に入れ替えて成り立つなら捨てる）→ 埋める物（大きい文字・色の面・本物の素材・中身）→ 通し表（全部の欄・全部の画面で、考えがどう出るか）。組み方（色・文字・構図）は taste-skill の `draw.mjs` に配ってもらい、考えを運べる物を選ぶ。本物の写真・古い地図・図版は `assets.mjs`・`fetch-photos.sh` で取る | `.github/factory/concept.md` |
| 2. 関門 | スクリプト（AIではない） | 機械で測れる事を測る：設計メモの形（持ち物8個以上・考えの1文・通し表3行以上）、**本物の絵の枚数**（出どころの記録がある画像だけを数える。ページは相談で3枚・本物の画面で4枚以上。道具の画面は問わない）、`lint.mjs` の FAIL（今ある見た目への追加は `docs/design.md` が上なので見ない） | `.github/scripts/design-judge.py gate`・`design-review.sh prepare` |
| 3. 審査 | 審査役（作ったAIとは別の Opus。読む・書くだけ、40 手まで） | **画像だけ**を見て（下へスクロールした続き・スマホ・実在のサイトの画像と並べて）、「はい・いいえ」の問いに答え、点（見た目 40%・使いやすさ 30%・考え 20%・中身 10%）と直し方を書く。コードも HTML も見ない。直し方は「消す」だけでなく「何で埋めるか」まで書く | `.github/factory/judge.md` |

**合格はスクリプトが決める**（`design-judge.py verdict`。AIに自分で合格と言わせない）：必ず通す問いが全部「はい」で、点が 7.5 以上で、関門が通っていること。

- 必ず通す問い：この題材だけの考えがある（`swap`）／本物の素材が主役の位置にある（`real`）／考えが下の欄・ほかの画面まで通っている（`through`）／地味でない（`full`）／AIの型が見えない（`tells`）／崩れが無い（`broken`）／オーナーが決めた事が絵に出ている（`owner`）。今あるアプリへの変更では、足した所が「このサービスらしさ」に沿っている（`fits`）
- 世界観・例の値・スマホの長さの3つの問い（11月17日の比較実験で、工場の見た目が普通の Claude Code に負けた指摘から。#117）：
  - `world`（必ず通す。「いいえ」は見た目の欄を 6.5 まで）：題材の世界観が最初の1画面で伝わる。白地・灰色の角丸・英字ロゴの無難な SaaS の見た目は「いいえ」。`looks`・`screen`・`change` で見る
  - `sample`（点の上限だけ。使いやすさの欄を 7.0 まで）：例の値が入力欄に見える。本物のような値（48,600円・10人など）が最初から入っていて入力欄と分からなければ「いいえ」。空欄・薄い例・「例」の表示は「はい」。`looks`・`screen`・`change` で見る
  - `short`（点の上限だけ。使いやすさの欄を 7.0 まで。**不合格にはしない**）：スマホのページが長すぎない。縦 5,000px 超、または主な操作が最初の1画面に入っていなければ「いいえ」。`screen`・`change` で見る（`looks` は最初の1画面だけの板なので見ない）。ページの縦が測れるときは、関門に `--phone-height PX`（390 幅で撮った高さ）を渡すと結果の JSON に入り、5,000px 超なら審査役の答えにかかわらず「いいえ」にする（`variety` と同じやり方）。測れなければ審査役の答えだけ
- 点の上限だけの問い：1秒で主役が1つ見える／同じ構図が続いていない（審査役が書いた構図の言葉が続いていれば、答えにかかわらず「いいえ」）／スマホで成立／実例の隣で見劣りしない
- 「いいえ」は、その欄の点に上限を掛ける（taste-skill の `references/critique.md` の上限を土台にした）。答えていない問いは「いいえ」。審査役が結果を書かなかったときは、合格とも不合格とも言わず「審査できなかった」と見せる
- 届かなければ、指摘の紙（`.judge/fix.md`）を作ったAIに渡して**1回だけ**直させ、もう一度審査する（審査は最大2回）。それでも届かなければ、止めずに、点と残った指摘を付けてオーナーに見せる（選ぶのはオーナー。完全に止めると、全自動でなくなる）
- 工場のデザイン担当では、直した後の審査の点が直す前より低ければ、直す前の物に戻して使う（直しで崩れが増えた物を残さない。#88 で 7.3 点 → 6.7 点になった）

**複数の案から選ぶ**（工場のデザイン担当。`design-judge.py pick`）：方向の違う案を別々のジョブで同時に作らせ、点の一番高い案を使う。時間は1案分のまま、選べる案が増える。

- 案の数は、ふだん 1。変数 `FACTORY_DESIGN_VARIANTS`（1〜3）で増やせる（ゲーム・相談で見た目を決めた物はいつも 1。ワークフローが決めて渡す。`pick` は案の数に依存しない）
- 案ごとに審査役が採点する（`verdict` を案ごとに行い、結果の JSON を `--out` に書く）
- 使う案：合格している案の中で `overall`（点）が最高の物。合格が無ければ最高点の案。同点は案の番号が小さい方。審査できなかった案（`judged` が false）は選ばない。全部審査できなければ番号は空（今までどおり「審査できなかった」扱い）
- 直しの回は、合格した案が無く、最高点が `PASS_LINE`（7.5）より 1.5 点以上低い（6.0 点以下）ときだけ行う（`pick` が `fix=true` を返す）。それ以外は直さずに選んだ案を使う
- `pick` は `index`（使う案の番号。0 始まり。選べなければ空）と `fix`（true か false）を `GITHUB_OUTPUT` に書く。`summary --picked N 結果...` が、各案の点と選んだ案を1行にする（案が1つのときの表示は今までどおり）

どこで動くか：

| 場面 | 作る役 | 審査する物 | 種類 |
| --- | --- | --- | --- |
| 工場の相談「見た目の方向」（`factory-talk.yml`） | 相談役（Opus・150 手。相談では直さない：審査1回で点と指摘を見せるだけ。11/19 の #250 で直しが効かなかったため） | 3つの方向の本物の最初の1画面（PC とスマホ）。3つが色違いでなく、考えから違うか（`distinct`） | looks |
| 工場の相談「ざっくり画面」（変数 `FACTORY_TALK_MOCKS=1` のときだけ） | 同じ | 2案を、PC は4画面ぶん・スマホは3画面ぶん下まで | screen |
| 工場のデザイン担当（`factory.yml`。ゲームは対象外） | デザイン担当（Opus・250 手。直しは 100 手） | できた本物の画面（最初のページを下まで、ほかのページ、スマホ）。直して確認コマンドが通らなくなったら、直す前の物に戻す | screen |
| 既存アプリの画面案（`claude-mocks.yml`） | 画面案のAI（Opus・150 手。直しは 80 手） | 2案を下まで | screen |
| Issue の実装（`claude-implement.yml`） | 実装AI（サイズで決まるモデル。直しは 50 手） | 変えた後の画面。足した所だけを見る | change |

**あとから画面を足しても「らしさ」を消さない**：工場のデザイン担当は、`docs/design.md` の最初の節 `## このサービスらしさ`（考え・しるし・埋める物・新しい画面を足すときの決め方・通し表）を書く。実装AIは、画面に触るときここを読み、審査役は足した所がそれに沿っているか（`fits`）を見る。

**既存アプリの作り直し**：画面全体の見た目を作り直す Issue（`ai:mocks`）では、画面案のAIは今の色・文字・部品の形に縛られない（今の画面は「何を載せているか」を知るためだけに見る）。最初に今の画面を審査役の問いで診断し、持ち物から考えを決め、組み方を配ってもらって2案を作る。オーナーが選ぶと、設計メモ（`ai-mocks` ブランチの `concept.md`）が実装AIに渡り、実装AIは `docs/design.md` の「このサービスらしさ」を書き直して、目標の画面に無い画面も同じ考えで作り直す。

相談の見た目は、ふだん「見た目の方向」の1回だけ：3つの方向を、それぞれ本物の最初の1画面（PC とスマホ。`look-N.html`）で見せ、選ばれた1画面がそのまま本番の土台になる（`factory-refs/issue/chosen-look.html`・`chosen-look.png`・`chosen-look-390.png`。下の欄とほかの画面は、デザイン担当が設計メモの通し表から作る）。11/19 の #250 では、方向とざっくり画面の2往復で、作り始めるまで AI だけで約70分かかった。変数 `FACTORY_TALK_MOCKS=1` を入れると、方向の後に今までどおりざっくり画面（下の欄まで2案）を出す。審査役に渡す紙の「オーナーが決めた事」は、見た目の段階の答えと注文だけ（案の段階の答えは「中身の決まり」。静止画に出せないので owner に使わない）。

相談の2つの段階の間では、設計メモと使った絵の出どころ（`credits.json`）を `factory-talk` ブランチに置いて引き継ぎ、作り始めるときはデザイン担当に渡す（`factory-refs/issue/chosen-concept.md`・`chosen-credits.json`）。オーナーに見せるコメントには、ざっくり画面の下の欄（2画面目）の絵と、審査役の点の行が付く。

## 進捗ログ

各工程が「使ったモデル・所要時間・結果」を、Issue の「進捗ログ」コメントに残す（`.github/scripts/step-log.sh`）。agent-desk の進捗図が、このコメントを機械で読んで表示する。記録するだけで、ラベル・自動修正・マージ・公開・モデルの切り替え方は変わらない。

### コメントの形式

- コメントは Issue ごとに1つだけ。先頭の行が目印 `<!-- ai-step-log -->`。これで探し、あれば編集、無ければ新しく作る（コメントは増えない）
- 次に、人が読む表（工程・モデル・所要時間・結果・修正）
- 最後に、機械が読む行を工程ごとに1行：`<!-- ai-step {JSON} -->`（工程の順に並ぶ）

```
<!-- ai-step {"step":"fix","model":"opus","started":"2026-11-15T07:32:00Z","finished":null,"result":"running","attempt":3,"max_attempts":3} -->
```

| 項目 | 値 |
| --- | --- |
| `step` | `plan` / `mocks` / `implement` / `ci` / `review` / `fix` / `deploy` |
| `model` | 実行時に `--model` へ渡した値そのまま（`opus`・`sonnet`・`fable` など）。モデルを使わない工程（`ci`・`deploy`）は `null` |
| `started` | 開始時刻（UTC の ISO 8601。例 `2026-11-15T07:28:00Z`） |
| `finished` | 終了時刻（同じ形）。未完了なら `null` |
| `result` | `running`（進行中） / `success` / `failure` |
| `attempt`・`max_attempts` | 修正（`fix`）のときだけ。何回目 / 最大3回 |

### どこで残すか

| 工程 | 残す所 | 進行中（`running`）も残すか |
| --- | --- | --- |
| `plan` | `claude-plan.yml`（AIの前に開始、`after-plan` で終了） | 残す |
| `mocks` | `claude-mocks.yml` の `publish`（終了だけ。開始時刻は `work` から渡す） | 残さない |
| `implement` | `claude-implement.yml`（AIの前に開始、`open-pr` で終了。結果は、PRができたか、またはAIが成功で終わったかで決める。AIが作業回数の上限を超えて「失敗」で終わっても、PRができていれば成功。PRを作るトークンが無く、人間がPRを作る構成では、AIが成功で終わっていれば成功） | 残す |
| `ci` | `pipeline.yml` の `after-ci`（終了だけ。開始時刻はCIの実行の開始時刻） | 残さない |
| `review` | `pipeline.yml` の `after-review`（終了だけ。モデルと開始時刻は、`claude-review.yml` が成果物 `ai-result` の `meta.json` で渡す） | 残さない |
| `fix` | `claude-mention.yml`（自動の修正依頼 `auto-fix` のときだけ。何回目かは依頼の「自動の依頼 n/3」から読む） | 残す |
| `deploy` | 残さない。公開の状態は、コミットの状態（`deploy/<種類>`・Vercel）に出るので、agent-desk はそちらを読む | - |

進捗ログのコメントは、どこでもワークフローのトークン（`github.token`）で書く。パイプラインの鍵が `PIPELINE_TOKEN`（オーナーのトークン）のリポジトリで、オーナーの名義のコメントが「質問への答え」（`answer.yml`）と間違われないようにするため。進行中を残さない工程が動いているかは、ラベルと Actions の実行で分かる。

### 更新のしかた

工程の開始前に `--result running`、終了後に `--result success` か `failure` で呼ぶ。同じ工程の行は上書きされる（`running` の行があれば `started` を引き継ぐ。修正は回数が進むので `--attempt` を更新する）。

```
.github/scripts/step-log.sh --pr 30 --step fix --model sonnet --result running --attempt 1 --max-attempts 3
```

- `--issue N` か `--pr N`（PR 本文の `Closes #番号` かブランチ名から Issue を引く）のどちらかを渡す
- `--model` には、そのワークフローが AI に渡している値をそのまま渡す。使わない工程は `null`
- 2つの工程がほぼ同時に書いても、行が消えないようにしている（CI の終わりとレビューの終わり、など。どちらも相手の行が無い古い表に足して書くので、後から書いた方が先の行を消す）。書いた2秒後（`STEP_LOG_VERIFY_WAIT`）にコメントを読み直し、自分の工程の行が無い・置き換える前の行に戻っていれば、今の表に足して書き直す（2回まで）。同じ工程のもっと新しい記録が入っていれば触らない。API は、ふつうは読み直しの1回が増えるだけ
- 2つの工程が同時に進捗ログを作ってコメントが2つになったら、後から作った方が、先のコメントに自分の行を足して、今作った自分のコメントを消す（コメントは1つのまま）
- 記録に失敗しても（gh のエラー・権限など）終了コードは 0。警告を1行出すだけで、パイプラインは止まらない

## 画面案が作れないとき・AIの結果の見える化

見た目の大きい Issue では、作る前に画面案（`ai:mocks`、`claude-mocks.yml`）を作る。AIは専用の手順書 `.github/factory/mocks.md`（置き場は `mocks/` だけ）を読んで作る。作れた画面案は、関門と審査役が見て、届かなければ1回直してからオーナーに見せる（上の「デザインの仕組み」。審査で止まることは無い）。AIが画面案を書かずに終わったとき（`mocks/mocks.json` が無い）は、止まらずに次の順で進む。

1. **その場で1回やり直す**：`work` ジョブの中で、拒否されたツールの名前を手がかりに付けて、もう一度AIを動かす（3回目は無い）
2. **それでも無ければ、案なしで企画へ**：`publish` が `MOCKS_RETRY=1` で `mocks-publish.sh` を動かす。画面案が無い・形が不正なら、`ai:mocks` を外して `ai:plan` を付け、「画面案は作れなかったので、案なしで進めます」とコメントする（拒否されたツール名も入る）。`ai:stuck` にはしない
3. 画面案が作れたときの動き（`ai:question` で選んでもらう）は変わらない

画面案のジョブが時間切れ・取り消しになって、この後片付け（`publish`）が動かなかったときは、`ai:mocks` が残る。これは見張り役が拾う（上の「自動でやり直す」の「画面案のまま、動きが無い」）。

`mocks-publish.sh` は、`MOCKS_RETRY` が無いときは `ai:stuck` で止まり、`0` のときは `retry=true` を出すだけで何もしない（どちらも古い workflow のための形。今の workflow は使っていない）。

`publish` の鍵は、ほかの workflow と同じく GitHub App の鍵 → `PIPELINE_TOKEN` → `github.token` の順に使う（`github.token` で付けた `ai:plan` では企画が動かないので、そのときは見張り役が拾うまで待つ）。

### ai-report.sh（AIの工程のあと、何が起きたかを残す）

AIが「正常に終わったのに何も残さなかった」とき、あとから理由を追えるように、どのAIの工程のあとにも `.github/scripts/ai-report.sh` が、実行記録から次をジョブのログと実行の Summary の両方に出す。

- 結果の種類（`success`・`error_max_turns` など）・手数・拒否の数
- 拒否された操作（そのままの形で最大5件）
- AIが最後に言ったこと（最大1,200文字）

```
.github/scripts/ai-report.sh --title "実装AI" FILE
```

ファイルが無い・壊れていても、いつも終了コード 0。企画は `after-plan`、実装は `open-pr`（どちらも main の版を動かす別のジョブ）、画面案と修正AIは同じジョブの中（画面案は `.github/` を読み取り専用にしてある。修正AIは API で取ってきた main の版）で動かす。レビューは作業フォルダがPRのコードなのでスクリプトを動かさず、同じ要点を `jq` で出す。

### denials.sh（拒否の中身を取り出す）

AIの実行記録から、許可されず拒否された操作（`permission_denials`）の `tool_name` と引数（1件あたり約200文字で切り詰め）を取り出す（`.github/scripts/denials.sh FILE`）。引数なしは件数と一覧、`--summary` は Summary 用の Markdown（`GITHUB_STEP_SUMMARY` に追記）、`--comment` はコメント用の短い文（「拒否されたツール：Write、Bash」）、`--check` は拒否が1以上なら終了コード 0・無ければ 1。`--check` 以外は、ファイルが無い・壊れている・拒否が無いときは何も出さず、終了コード 0。

### 成果が無いまま終わったときの動き（まとめ）

| AI | 成果が無いとき |
| --- | --- |
| 企画AI | `plan-result.txt` が無ければ、2回まで自動でやり直し（`ai:retry`）、続くなら理由を書いて人間に回す（`after-plan.sh`） |
| 画面案 | その場で1回やり直し、それでも無ければ案なしで企画へ（上）。後片付けが動かず `ai:mocks` のまま止まったら、見張り役が1回やり直し、2回目は人間に回す |
| 実装AI | 拒否があれば、手がかりを書いて1回だけやり直す。拒否が無ければ、AIが最後に言ったことを書いて人間に回す（`open-pr.sh`） |
| レビューAI | まとめのコメントが無ければ、2回まで自動でやり直し、続くなら人間に回す（`after-review.sh`・見張り役） |
| 修正AI | 理由を分けて動く（上の `classify_no_change`）。実行記録は `claude-mention.yml` が成果物 `ai-result` で `after-mention` に渡す |

## 順番待ちの進め方（`ai:queue`）

企画AIは、清書した本文の最後に「触るファイル」の印（`<!-- ai-touches: src/lib/a.ts, src/components/ -->`。/ で終わる物はフォルダ）を書く。順番待ちを進めるとき（`queue-next.sh`・見張り役。`pipeline-lib.sh` の `start_next_in_queue`）：

- 進行中の物（`ai:implement` の Issue・open のPR）が無くても、先頭の1つで終わらない。先頭を始めたあと、下の繰り返し（上限・重なり・印の無い物の決まり）に入り、上限まで並べて始める（触るファイルが重ならない物が3件・上限3なら、1回の実行で3件）。先頭は `priority:high` が付いた物、その中は番号の小さい順。印の無い物は、触るファイルが分からないので、その1つを始めたら、この実行では続けない（今までどおり）
- 企画が同時に終わったとき：`after-plan.sh` のジョブは1つずつにしない（`concurrency` は待っている実行を置き換えで取り消し、3件以上同時だと真ん中の企画の結果が消える）。代わりに、`ai:implement` を付けた**あと**にもう一度数える（`pipeline-lib.sh` の `yield_if_crowded`）。番号の小さい実装中の Issue が上限の数以上ある、または触るファイルが重なるなら、番号の大きい方が `ai:implement` を外して `ai:queue` に入れ直す。引く側は番号だけで決まるので、2つが互いを見ても両方は引かない。付ける**前**にずらして数える案もあるが、ずらしても同時に数えれば同じ結果になり確実ではない。付けたあとに数えれば必ず相手が見えるので、こちらにした。ただし `ai:implement` を付けた時点で実装のワークフローは始まっているので、引いた Issue の実装が一度起きてしまうことはある（ラベルは `ai:queue` だけになり、`ai:queue` と `ai:implement` を同時に持たない。順番が来れば、あらためて始まる）
- 並列の上限は、時間帯と手の上書きで決まる（`pipeline-lib.sh` の `parallel_limit`。現在時刻を引数で受ける純粋な関数で、`start_next_in_queue` と `after-plan.sh` が同じ物を使う）。値は環境変数（Actions の Variable を、`queue.yml`・`watchdog.yml`・`claude-plan.yml` がワークフローの `env` で渡す。2026-11-18 まで渡しておらず、設定を変えても既定の3で動いていた）。上限は 1 以上の整数で、数でない・0 以下は既定値に戻す。全部空なら今までどおり 3
  - `PARALLEL_DAY`：昼の上限。無ければ `MAX_PARALLEL`（既定 3）
  - `PARALLEL_NIGHT`：夜の上限（既定 1）
  - `PARALLEL_NIGHT_HOURS`：夜の時間帯。`"01-08"`（開始時-終了時。開始を含み終了を含まない＝1:00〜7:59）。`"22-06"` のように日をまたいでもよい。空・形が違う・開始と終了が同じなら夜は無し（いつも昼の上限）
  - `PARALLEL_TZ`：時間帯の基準（既定 `Asia/Tokyo`）
  - `PARALLEL_OVERRIDE`：手の上書き。`"night until 2026-11-18T08:00+09:00"`（`night`＝夜の上限、`day`＝昼の上限、期限は ISO 8601。時刻だけで書けば `PARALLEL_TZ` の時刻）。期限まで時間帯の決まりに勝ち、期限を過ぎた・形が違うときは無視する
  - 夜になっても動いている作業は止めない（ラベルも外さない）。新しく始める数だけが減る（`busy`＝AIがいま動かしている実装の数が上限以上なら始めない。数え方は下の「止まっている物」の項）。`after-plan.sh` も同じ上限・同じ数え方（`count_active_implementing`）を使うが、このリポジトリの `busy == 0` のときは、全部のリポジトリで上限に達していなければ1件は始める（触るファイルが進行中の物と重なるときは待つ。全部のリポジトリで上限に達していれば順番待ち）。ログの「並列の上限」には、昼か夜か・上書き中かも書く
- **上限は、同じ持ち主の全部のリポジトリで合わせて数える**（Variable `PARALLEL_SCOPE`。未設定・`global` なら全部、`repo` なら今までどおり、このリポジトリだけ。2026-11-19 にオーナーが「全部のリポジトリ合わせて1つ」を選んだ。Claude の使用量はアカウント全体で共通なので、リポジトリごとに数えると、夜の「1件ずつ」がリポジトリの数だけ同時に動いた）。`pipeline-lib.sh` の `start_next_in_queue` が、最初に `parallel_scope_resolve` で広さを決める
  - 動いている数：このリポジトリは今までどおり `count_active_implementing`。ほかのリポジトリは、Search API（`user:<持ち主> is:issue is:open label:"ai:implement"` と `label:"ai:queue"`）で Issue のあるリポジトリを見つけ、そのリポジトリの開いている一覧を読み直して、同じ決まり（`active_implementing_numbers`。止まった物・長いマージ待ちは数えない）で数える。ログは「全部のリポジトリで実装中 N（o/r 1・o/r2 0）」
  - 始める物：空きがあれば、全部のリポジトリの `ai:queue` から、`priority:high` を先に、その中は `ai:queue` が付いた時刻（Issue のイベント）の古い順（`global_queue_order`。時刻の分からない物は最後）。このリポジトリの順番待ちは検索ではなく一覧から読む（付けたばかりの `ai:queue` を、検索の反映の遅れで見落とさない）。重なり・印の無い物の決まりは、そのリポジトリの中で今までどおり（`queue_try_start`。毎回そのリポジトリの一覧から進行中の物を数え直す）。重なって始められない物は飛ばして次。始めるのは今までどおり `ai:queue` を外して `ai:implement` を付けること（ほかのリポジトリの Issue にも付ける。付けたリポジトリの実装が動き出す）。1回の実行で、全部の数が上限に届くまで並べて始める
  - 取り合い：2つのリポジトリの順番待ち（や企画のあと）が同時に動くと、互いの始めた物を見ずに上限を超える。始めたあとに `QUEUE_RECOUNT_WAIT_SEC`（既定 5 秒。検索の反映の遅れを吸収する）待って全部で数え直し（`global_yield_overflow`）、上限より多ければ、席に着いた時刻（`ai:queue` が付いた時刻。無ければ `ai:implement`）の古い順に上限の数だけ残し、残りのうち**自分が始めた物だけ**を `ai:implement` を外して `ai:queue` に戻し、その Issue に「全部のリポジトリで並列の上限を超えたので、順番待ちに戻しました」とコメントする（`global_overflow_pick`。時刻の分からない物は古い扱いで、前から動いている物は追い出さない。2つの実行が同じ一覧を見れば、同じ物を戻す）。数え直しは、このリポジトリ・最初に見つけたリポジトリ・始めた物のリポジトリを一覧から読み、検索に出ていない物も拾う
  - 黙って広げない：検索が使えない、見つけたリポジトリが鍵のインストール（`installation/repositories`。GitHub App の鍵のときだけ見る）に入っていない、そのリポジトリを読めない（403・404）ときは、このリポジトリだけで数える（`repo` に落とす）。ログに `::warning::` と、実行の Summary に「⚠️ 並列の上限を、このリポジトリ（o/r）だけで数えています：理由」を出す。Doctor も同じ判定で ⚠️ を出す（`doctor.sh` の `check_parallel_scope`）
  - 見張り役の目覚まし：自分に順番待ちが無く、ほかのリポジトリにだけ順番待ちがあるときは、テンプレートのリポジトリだけが、並列の上限が変わる時刻にかける（距離に関係なく。全部で枠1つ。夜が明けたら、起きたテンプレートの見張り役が、ほかのリポジトリの順番待ちも始める）。ほかのリポジトリはかけない（開発していないリポジトリが枠を食わない）
  - 鍵：ワークフローの鍵（`create-github-app-token`）に `owner: ${{ github.repository_owner }}` を付け、持ち主のリポジトリ全部に効くようにしてある（`queue.yml`・`watchdog.yml`・`claude-plan.yml`）。App が入っていないリポジトリは数えられないので、上の ⚠️ になる
- 進行中の物があっても、並列の上限（上の決まり。何も設定しなければ 3）に達しておらず、触るファイルが進行中の物と重ならない物は、並べて始める。重なりは「同じファイル」「片方のフォルダの中にもう片方がある」。進行中の物の触るファイルは、PRがあればPRの変えたファイル（配布・依存の更新など AI 以外のPRも）、PRがまだ無ければ Issue の印
- 仕様書（`docs/` の下の `.md`。サブフォルダの中も）は、重なりに数えない（`paths_overlap` が除く）。agent-desk の Issue はほぼ全部が `docs/spec.md`・`docs/design.md` を触るので、数えると全部が重なって1件ずつになった。後からマージされる方は、main を取り込むときのコンフリクトを、今までどおりAIが解く（`request_fix_or_stop`。文書は両方を残せば解ける）。`docs/` の下でも `.md` 以外（画像など）は数える
- 見た目のテスト（`tests/visual/`）があるリポジトリでも、画面のファイル（`app/`・`components/` など）は、同じファイル（フォルダ指定との包含を含む）を触る物だけ待つ。別の画面のファイルどうしは並べる。基準の画像のずれは、後からマージされる方の自動の撮り直し（`after-ci.sh` の `visual:update`、2回まで）で直る
- 印の書き方：触るファイルを1つずつ書く。フォルダ（/ で終わる）で書いてよいのは、新しく作るフォルダ（中身が全部この作業の物）だけ。`src/components/`・`src/lib/`・`src/app/`・`tests/`・`docs/` のような、ほかの作業も使う大きなフォルダは書かない（フォルダは中の全部と重なり扱いになり、ほかの順番待ちが全部待たされて、並列の上限が5でも1件ずつになった。agent-desk #461）
  - 仕組みの側でも守る：企画のあと（`after-plan.sh`）、READY の印に広すぎる物があれば、`pipeline-lib.sh` の `touches_too_broad` が見つける。広い物＝末尾が `/` で、深さ（`/` で区切った部品の数）が2以下のフォルダ（`src/`・`src/components/`・`tests/visual/`・`docs/` など）。ファイルと、深さ3以上の新しいフォルダ（`src/app/(app)/lanes/`）は許す。一覧は `pipeline-lib.sh` の中にあり、`pipeline.json` には足さない。進行中の作業が無いときも、READY のたびに確かめる
  - 広い物があれば、Issue に「触るファイルが広すぎるので、並べて始められません」のコメント（1行目の印 `<!-- touches-too-broad -->`。広い物の一覧と「ファイル単位で書き直してください」つき）を書き、`ai:implement`・`ai:queue`・サイズのラベルは付けずに `ai:plan` を付け直して、企画AIに書き直させる。やり直しは1回で、前に印のコメントがあれば、今までどおり進める（重なれば待たせる）
- 印を書き忘れた Issue：企画のあと（`after-plan.sh` の `ensure_touches_mark`）に、READY なのに本文に印が無ければ、本文のバッククォートで囲んだファイル名（`src/lib/a.ts` など、/ を含む物）から印を作って本文の最後に足す。ファイル名も無ければ印は無いままで、上の決まりで待つ
- 印の無い物・進行中の物に印の無い物があるときは、進行中の物が全部終わるまで待つ。ただし、数える進行中の物が1つも無い（実装中の Issue も、数えるPRも無い。開いているのが数えないPRだけ）ときは、印の無い物も始める。印の無い物は1回の実行で1つだけ（始めたあとは、その実行では続きを待つ）
- 一部だけ直したPR（`Refs #N`）がマージされた Issue も、この順番待ちに戻る：残り（PRの説明の未チェックの行）のコメントを書いて `ai:queue` を付け、次の実装AIが同じ Issue の続きをやる。3回目の `Refs` のマージでは戻さず、`ai:stuck` で人間に回る（上の「自動でやり直す（人間に回さない）とき」）
- 止まっている物（`ai:stuck`）は数えない。`ai:stuck` が付いたPR（配布のPRなど）も、進行中から外す
- 並列の上限と比べる「実装中の数」（`busy`）は、AIがいま動かしている物だけ（`count_active_implementing`）。`ai:implement` の開いている Issue のうち、次は席に数えない：`ai:stuck` が付いた Issue、PR（head が `claude/issue-N-`）が `ai:stuck` の Issue、人間のマージ待ちが `HOLD_BLOCK_MIN` を過ぎたPR（`hold_prs` の `expired`）の Issue。60分以内のマージ待ちと、時刻やラベルが読めない物は数える。一覧が読めなければ失敗（順番待ちは進めない）。夜（上限1）に1件が止まっても人間のマージ待ちになっても、朝まで順番待ちが止まらない。ただし触るファイルの側は変えない：止まった実装中の Issue でPRがまだ無い物の印は進行中に数えたままで、重なる順番待ちは待つ。ログの「実装中 N」もこの数
- 人間のマージ待ち（`ai:hold` が付いていて、レビューまで済んでいる。`watchdog.sh` と同じ判定）のPRが、環境変数 `HOLD_BLOCK_MIN`（既定 60 分）より長く待たれているときは、そのPRの変えたファイルを「進行中」から外し、重なる順番待ちも始める（並列の上限 `MAX_PARALLEL` は守る）。待ち時間は、そのPRに `ai:hold` が付いた時刻（PRのイベント）から数える。時刻が読めないとき・CIやレビューが済んでいない `ai:hold` のPRは、時間に関係なく今までどおり進行中に数える。`after-plan.sh` も `inflight_touches` を使うので、同じ扱いになる。外れる時刻には何のイベントも起きないので、順番待ちがあるとき、見張り役はその時刻（`ai:hold` が付いて `HOLD_BLOCK_MIN` 分＋1分）にも目覚まし（`retry-timer.yml`）をかける（定期の起動は数時間遅れることがあり、順番待ちが止まり続けた。PR #162 のとき）
  - 外したPRには、「待たずに #番号 を始めます。あとで入る変更とコンフリクトしたら、AIが解消します」と1回だけコメントする（印 `<!-- hold-released: #番号 -->`）
  - 順番待ちを止めている（時間内の）`ai:hold` のPRには、「このPRをマージすると #番号 が動き出します」というコメントを1つ付ける。1行目の印は `<!-- hold-blocking: #2,#3 -->` で、待っている Issue の番号を全部書く（agent-desk が読める）。待つ Issue が変わったら書き換え、待つ Issue が無くなったら（60分を過ぎて始まった・閉じられたなど）印を `<!-- hold-blocking: -->` にして「今は止めていません」に書き換える
  - `ai:hold` のPRが main とコンフリクトしたら、見張り役（`watchdog.sh`）が、他のPRと同じくAIに解消を頼む（同じ先頭コミットには1回。上限を超えたら人間に回す）
- 企画のあと（`after-plan.sh`）も同じ重なりを見る：企画AIの「並列でよい（PARALLEL）」は、企画を始めた時点の進行中の作業を見た判断なので、企画の間に別の Issue の実装が始まっていると（Issue をまとめて書いたとき）、その作業とは見比べていない。この Issue と進行中の物の両方に印があって重なれば（仕様書は数えない）、PARALLEL でも順番待ちにする。どちらかに印が無ければ、企画AIの判断

## 使ってみる役・監査役（`claude-try.yml`・`claude-audit.yml`）

「他人が一人で、会話なしで使える」と「仕様書が食い違っていない」を、パイプラインが自分で確かめる。見つけた問題は Issue（`ai:found`・`ai:plan`）にして、いつもの流れ（企画→実装→…）で直す。

| 役 | いつ動く | 何をする | 上限 |
| --- | --- | --- | --- |
| 使ってみる役（`claude-try.yml`） | 毎日 21:13（日本時間）。ただし公開しているサイトの URL があり、直近24時間の main に、アプリの中身が変わったコミットがある日だけ（＝公開があった日。1日1回まで） | 初めて使う利用者として、本番のサイトを本物のブラウザ（`shot.mjs`）で 390・1440 の幅で開き、`docs/spec.md` の主な使い方を試す。壊れている・迷う・崩れている所を探す（好みの問題は書かない。ログインが要るサービスでは、ログインの手前の画面だけ） | 1回に最大3件 |
| 監査役（`claude-audit.yml`） | 毎週月曜 3:41（日本時間）。ただし進行中の作業（`ai:plan`・`ai:implement`・`ai:review`・`ai:queue` の Issue、`claude/` のPR）が無いときだけ。`docs/spec.md` が無いリポジトリでは動かない | 仕様書の中・仕様書とデザイン仕様・仕様書とコードの食い違いを探す。どちらに合わせるかと、直すときに触るファイルも書く（誤字・好み・まだ作っていない機能は書かない） | 1回に最大3件 |

- 使ってみる役は、本番が main の最新に追いついているときだけ動く（main の先頭に公開のステータス（`Vercel`・`deploy/…`）が無く、それより前のコミットにある＝追いついていない。先頭の公開が公開中・失敗のときも待つ。パイプラインの物（`.github/`・`docs/pipeline.md`・`docs/pipeline-setup.md`・`.claude/`）しか変わっていないコミットは公開されないので、飛ばして見る）。公開はマージが落ち着いてからまとめて行うので、追いつく前に試すと、main ではもう直った不具合を Issue にしてしまうため（tochi-rirekisho #9・#11）
- 使ってみる役は、パイプラインの配布だけの日は動かない。直近24時間の main のコミット（30件まで）で変わったファイルが、どれも `.github/`・`docs/pipeline.md`・`docs/pipeline-setup.md`・`.claude/` だけなら見送る（本番は変わっていないのに、毎日AIを動かさないため）。変わったファイルを読めなかったコミットは、アプリの変更として数える（試さない方へは倒さない）。30件以上あれば、中身を読まずに動かす
- 動かすかは `found-gate.sh try|audit` が決める。公開先の URL は、GitHub Pages の公開があればその URL、無ければリポジトリの「Website」（工場が公開先を書く）。テンプレートのリポジトリ（ai-dev-template 自身）と、`docs/spec.md` が雛形のままのリポジトリでは、使ってみる役は動かない（Website に別のリポジトリの本番が入っていると、そのサービスを違う仕様書で試してしまうため。`force` でも動かない）。Actions の画面から手で動かすと（`force`）、日付・進行中の条件を見ずに動く
- AIは結果を `.try/result.json`・`.audit/result.json`（`{"findings":[{"title","body"}]}`）に書くだけ。Issue は、別のジョブ（`report`）が main の版の `found-report.sh` で作る（AIのジョブにはパイプラインの鍵を渡さない）。同じ題名の `ai:found` の Issue が開いていれば作らない（空白の違いは無視）。開いている `ai:found` の Issue が6件（`FOUND_OPEN_MAX`）以上あるときは、新しく作らない（AIは同じ問題にも毎回ちがう題名を付けるので、直る前に積み上がるのを止める。人間の返事待ちの `ai:skip` は数えない）
- AIを動かす前に、もう報告してある問題（開いている `ai:found` の Issue と、直近14日に閉じた物）の題名を `.try/known.md`・`.audit/known.md` に書いて渡す（`found-known.sh`）。AIは同じ問題にも毎回ちがう題名を付けるので、「言い方が違っても同じ物なら書かない」と頼む
- 撮った画像は、その実行の artifact（`try-out`・14日）に残り、Issue の本文にログの場所を書く
- モデルは sonnet（使う量を抑えるため）。手数の上限は 使ってみる役 60・監査役 80
- AIが結果のファイルを書かずに終わったとき（使用の混み合い 529 など）は、その場で1回だけやり直す。それでも無ければ「確かめられていない」と警告を残す（「問題なし」とは扱わない）
- 長くなりすぎた節（目安：1つの節が約40行を超え、重複や言い換えが多い）を、意味を変えずに短くまとめる提案も、監査役が出せる。結果の `findings` の要素に `"kind":"shorten"` を書く（`body` には元の節の見出し＝ファイルと見出しの文字と、短くした文案）。`found-report.sh` は、この案に `ai:found` と `ai:skip` を付けて作る（`ai:plan` は付けない）。本文の最後に `<!-- ai-found-kind: shorten -->` の印が付く
  - 人間が確認するまで、実装には回らない。**意味を変えない**（決まり・数値・例外を落とさない）案だけを出し、迷う節は出さない。人間が案を読んで良ければ `ai:skip` を外すと、企画に回る
  - 枠は食い違いと合わせて1回に最大3件（`FOUND_MAX`）。同じ題名の重複チェックも同じ

## 他の Issue・PR の完了待ち（`ai:blocked`）

「別の作業の結果や決まりが無いと、清書も実装も始められない」Issue を、人間が回し直さなくても進める仕組み（例：ai-dev-template で形式が決まり、アプリのリポジトリに配られてから始める作業）。

1. 企画AIが `plan-result.txt` の1行目に `BLOCKED`、2行目から下に待ち先を1行に1つ書く（`owner/repo#番号`。このリポジトリなら `#番号`。Issue・PR の URL でもよい。最大10件）。あわせて、何を待っているかを Issue にコメントする
2. `after-plan.sh` が `ai:blocked` を付け、待ち先の印 `<!-- blocked-by: owner/repo#N -->`（待ち先ごとに1つ）をコメントに書く。待ち先が1つも読み取れなければ、理由を書いて人間に回す
3. 見張り役（`watchdog.sh`。定期の起動（ほとんど来ない）と、ほかの作業が終わるたび。続けて終わるときは10分の枠に1回。待ちが残っている間は15分ごとの目覚まし）が、いちばん新しい待ち先のコメントの印を読み、待ち先の状態を見る（Issue も PR も `issues` の API で読める。PR はマージ・クローズで `closed`）
   - 全部 `closed`：`ai:blocked` を外して `ai:plan` を付ける（企画AIが、待ち先の結果を読んで清書する）
   - 1つでも開いている：待つ
   - 読めない待ち先がある：戻さない（間違って再開しない）。読めないまま60分（`BLOCKED_UNREADABLE_MIN`）たったら、理由を書いて人間に回す
4. 別のリポジトリの待ち先は、公開リポジトリならパイプラインの鍵で読める。非公開のリポジトリは、鍵がそのリポジトリも読めるときだけ

進行中の作業と同じ場所を触るだけ（結果を使うわけではない）なら、`ai:blocked` ではなく順番待ち（`ai:queue`）を使う。

## Supabase を起こしておく（`supabase-keepalive.sh`）

Supabase の無料プランは、1週間データベースの操作が少ないと、プロジェクトを一時停止する。止まると、公開したアプリの会員・課金・保存が動かず、表の変更（`deploy-supabase.sh`）も流せない（11/21、tide-almanac が 11/12 頃から止まっていて、表の変更が4回とも `tenant/user ... not found` で落ちていた。画面には「ログを見てください」としか出なかった）。

- `supabase-keepalive.yml` が毎日 05:43（日本時間）に `supabase-keepalive.sh` を動かす。公開先（`pipeline.json` の `deploy`）に `supabase` があるリポジトリだけで、小さな表 `app_meta.heartbeat`（1行だけ）に今の時刻を書く。つなぐだけでは操作に数えられないので、書き込みをする。`supabase` が無いリポジトリでは何もしない
- もう止まっていたら、ワークフローを失敗にして、スマホに知らせる（`notify.sh` の `deploy_failed`）。起こすのは人間（Supabase のダッシュボードで Resume project）
- 渡す秘密は `SUPABASE_DB_URL` と通知のトピックだけ。アプリのコードは動かさない（`.github/scripts` と一番上のファイルだけを取り出す）
- 表の変更の公開が失敗したときも、同じ判定（`supabase-lib.sh`）で理由を公開の状態の説明に書く（止まっている・パスワードが違う・つながらない）。当てはまらなければ今までどおり「ログを見てください」。説明に入れるのは決まった文だけ（psql の文そのものは入れない）

## Vercel の使用量の見張り（`vercel-usage.sh`）

Vercel の Hobby は、30日の使用量が上限に届くとアカウントごと止まる（11/20 に、Fluid Active CPU が 6h25m / 4h で止まった）。止まる前に気づくため、`.github/scripts/vercel-usage.sh` が1日1回、使用量を見る。

- 動かす所：`.github/workflows/vercel-usage.yml` が毎日 03:17（日本時間。`cron: "17 18 * * *"`）に動かす（手でも動かせる）。テンプレート本体だけで動く（最初のジョブが API で `is_template` を確かめ、配ったアプリでは何もせず終わる）。Vercel の鍵 `VERCEL_TOKEN` は、工場と同じ Environment `factory` に置く。Issue を作る鍵は `FACTORY_TOKEN`（無ければ `github.token`）。通知は `NTFY_TOPIC`・`NOTIFY_EVENTS`
- 読む物：`npx --yes vercel@latest billing usage --since 30d --group-by project`（まず `--format json`、だめなら指定なし）。鍵は環境変数 `VERCEL_TOKEN` だけで渡し（`--token` は使わない）、出力に混ざっても伏せる。チームは `VERCEL_TEAM_ID`（`--scope` で渡す）
- 上限：スクリプトの中の表（Fluid Active CPU 4時間・Fast Origin Transfer 10GB・Function Invocations 100万回・CDN Requests 100万回・Fluid Provisioned Memory 360GB-Hrs）。`VERCEL_PLAN=pro` なら何もしない
- 知らせ方（項目ごと）：
  - 50% を超えた：スマホに1回（`notify.sh` の種類 `usage`。既定の通知に入っている）
  - 75% を超えた：いちばん使っているプロジェクトのリポジトリに Issue（`priority:high`、題「Vercel の使用量が上限の75%：<項目>」、本文に量・割合・プロジェクトごとの内訳）。同じ題の開いた Issue があれば作らない。リポジトリは `VERCEL_REPO_MAP`（`プロジェクト名=owner/repo` をカンマ区切り）で決め、対応が無ければ `GITHUB_REPOSITORY`
  - 90% を超えた：その Issue にコメントを足し、もう一度スマホに知らせる
  - 1日で上限の15%以上増えた：50%未満でも、スマホに知らせる（急に増えたのは、何かが壊れている合図）
- 同じ段で毎日鳴らさない：前の記録より段が上がったときだけ鳴らす。記録は、閉じた Issue（`VERCEL_LOG_ISSUE`、既定 212）に、1日1回コメントで残す（1行目が `<!-- vercel-usage {…} -->`）。同じ日に何度動かしても、通知もコメントも増えない
- 取れなかったとき（鍵が無い・CLI のエラー・出力の形が変わった）は、`::warning::` を1行出して 0 で終わる（見張りを止めない）
- 出力の読み方（CLI の出力は実物で確かめてから直す前提）：JSON の配列（または `data`・`usage`・`rows`・`items` の中の配列）の1行を「プロジェクト・項目名・量」と読み、量は表の単位とみなす（行に `unit` があれば bytes→GB、seconds・ms→時間に直す）

## 見張り役から agent-desk の自己点検を呼ぶ（`selfcheck-call.sh`）

`watchdog.yml` の「agent-desk の自己点検を呼ぶ」段が、`.github/scripts/selfcheck-call.sh` で agent-desk の `POST /api/selfcheck` を呼ぶ。AI は使わない。

- 動く条件：変数 `AGENT_DESK_URL` があり、起動が `workflow_run` ではない（定期の起動と目覚ましの時だけ。ワークフローが終わるたびには呼ばない）、App の鍵が取れて、API で確かめて `is_template` が true（テンプレート本体だけ。配ったアプリの見張り役からは呼ばない）
- 結果：404 は黙って飛ばす（入口がまだ本番に入っていない）。2xx は結果を1行出す。401・5xx・30秒の時間切れ・つながらない時は `::warning::` を1行出す
- 失敗しても見張り役を止めない（段は `continue-on-error: true`・1分の枠で、スクリプトの終了コードは常に 0）。鍵は curl の引数に出さず、標準入力のヘッダで渡す

## 公開先の決め方：サーバーの要らないアプリは GitHub Pages（`pick-deploy.sh`・`move-to-pages.sh`）

Vercel の Hobby は CPU の上限で止まると、サーバーの要らないアプリまで公開できなくなり、非商用だけという決まりもある。そこで、**サーバーで動く物が無いアプリは GitHub Pages、サーバーが要る物だけ Vercel** にする。

- **決める関数**：`.github/scripts/pick-deploy.sh` の `pick_deploy <言語> <説明> [課金 yes|no] [ログイン yes|no]` が `github-pages` か `vercel` を返す。迷ったら `vercel`（サーバーが要るのに Pages に出すと壊れるため）
  - 言語が `nextjs` 以外（`saas`・`python`・`game`・`webgame`）は `vercel`（`game`・`python` は別の公開先が決まっている）
  - 課金・ログインが `yes`、または説明にサーバーで動く物を思わせる言葉（API・ログイン・会員・課金・AI・メール・共有・データベース・Supabase・Stripe など。「サーバー不要」は数えない）があれば `vercel`
  - 説明にサーバーの要らない印（データは端末・静的・ポートフォリオ・ゲーム・サーバー不要など）があるときだけ `github-pages`
- **工場**（`factory.sh`）：`pick_deploy` が `github-pages` なら、`pipeline.json` の deploy を `[{"kind":"github-pages","build":"PAGES_BASE_PATH=/<リポジトリ名> npm run build"}]` にし、`next.config.ts` を `output: "export"`・`trailingSlash: true`・`images: { unoptimized: true }`・`basePath`（公開のビルドだけ `PAGES_BASE_PATH` から）にする。`vercel.json` は消し、Vercel のプロジェクト・鍵は作らず写さない。Pages は工場が有効にする。どちらにしたかと理由は、最初のコメントと、サービスの `docs/spec.md`（「公開先」の行）に1行書く。課金・ログインの有無は、環境変数 `APP_PAID`・`APP_LOGIN`（`yes`）で渡せる
- **今あるアプリを移す**：`GH_TOKEN=… .github/scripts/move-to-pages.sh <owner/repo>`（マネージャーが手で使う）。サーバーで動くファイル（`app/api/`・`route.ts`・`middleware.ts`・`"use server"`・`supabase/migrations`）があれば、理由を出して止まる。無ければ、上と同じ `pipeline.json`・`next.config.ts` にする PR（ブランチ `move-to-pages`）を作り、Pages を有効にする（もう有効なら飛ばす）。素の `<a href="/…">`・`<img src="/…">`（`basePath` が付かない）を探し、PR の本文に一覧を書く。`next/link`・`next/image` は自動で付く
  - 静的な書き出しで壊れる物でも止まる（理由に一覧を出す。それぞれ5件まで）：`generateStaticParams` が無い `[id]` のページ（`/x/?id=…` にしてブラウザで読む）、`"use client"` の無いサーバーのページで `searchParams` を読んでいる物（ブラウザの `useSearchParams` にする）
  - 素の `<a>`・`<img>` のほかに、CSS の `url(/…)` と、コードの中の素材の道（`"/photos/a.jpg"` のように文字で書いた `.png`・`.jpg`・`.webp`・`.svg`・`.mp4`・`.glb`・`.woff2`・`.json` など。`next/image` に文字で渡すと `basePath` が付かない。`next.config` とテストは除く）も、PR の本文の一覧に入れる
- **Pages の有効化**（`deploy.yml` の `pages-enable`）：公開のたびに、`pages` の前に別のジョブで、Pages がまだ無効なら有効にする（Source を GitHub Actions に。`POST repos/<リポジトリ>/pages` の `build_type=workflow`）。`github.token` には権限が無いので、App の鍵 → `PIPELINE_TOKEN` の順で試す。アプリのコードが動くジョブに鍵を渡さないよう別のジョブにしてある。どちらでも有効にできなければ `::warning::` だけで続け、その後の `pages` が 404 で落ちる（Settings → Pages の Source を GitHub Actions にして、公開をやり直す）
- 移したあと、Pages が動くのを見てから Vercel のプロジェクトを止める

## スクリプトのテスト

`.github/scripts/tests/` に、進行役のスクリプトのテストがある。本物の GitHub には触らず、疑似の `gh`（`tests/fake-gh`）が状態をファイルに持つ。

- 全部実行：`.github/scripts/tests/run-all.sh`（CIの `script-tests`、`shellcheck` も同じ物を見る）
- `run-all.sh` は、テストのファイルを並べて動かす（1本ずつだと、CI の時間切れ（10分）に届いてPRが止まったため）。並べる数は CPU の数（`nproc`）で、環境変数 `TEST_JOBS` で変えられる（`TEST_JOBS=1` なら1本ずつ）。結果は、終わった順ではなくファイル名の順に、今までと同じ形で出す。時間のかかる `test-run-as-app.sh`・`test-factory.sh` は先に始める
- 並べて動かすので、テストは固定の場所（`/tmp/決まった名前`、テストのフォルダの中、リポジトリの中）に書かない。`mktemp -d` か `setup_mock` の `MOCK_DIR` の中だけを使う。`pipefail` のスクリプトでは、変数の中身を `printf … | grep -q` で探さず、`grep -q … <<< "$変数"` と書く（`grep -q` は見つけた所で読むのをやめるので、混んでいると書く側が途中で切られ、「無い」になることがある。`test-run-all.sh` が書き方を見張る）
- 書き方は `tests/lib.sh` の冒頭。スクリプトを変えたら、場面に合うテストを足す
- 変更を入れる前にテストを壊してみて（わざとバグを入れる）、テストが落ちることを確かめると確実
- テストは `.github/` ごと全部のアプリに配られ、アプリの CI でも動く。テンプレートにしか無い物（`examples/` など）に頼るテストは、先頭で「無ければ飛ばす」と書く（`test-factory.sh` の先頭と同じ書き方。`test-sync-to-apps.sh` が書き忘れを見つける）。配り先の形で全部のテストが通るかは、`.github/scripts/tests/run-as-app.sh` で確かめられる。アプリごとに形の違うファイル（`vercel.json`・`package.json`・`pipeline.json`・`CLAUDE.md`）を読むテストを見逃さないよう、形の違う見本のアプリを5つ（`.github/scripts/tests/app-fixtures/` の `next-vercel`・`webgame`・`electron`・`python`・`visual-keep`）置いてあり、見本ごとに「一時フォルダに見本を写す → `git init` → `sync-to-apps.sh --local` → コミット → `run-all.sh` と `shellcheck`（CI と同じ書き方）」を回す。1つ落ちても残りは回し、最後に落ちた見本の名前を出して失敗で終わる（`app-fixtures/` は配り先には配らない。`test-run-as-app.sh` が仕組みを確かめる）。環境変数 `SYNC_CANARY`（空白区切りの `owner/repo`。例 `Gaku1205/agent-desk Gaku1205/tap-stack-rush`）があれば、その公開リポジトリを `git clone --depth 1`（トークンなし）して同じ手順も回す（空なら何もしない）。テンプレート本体の CI も同じ物を動かし（`script-tests-as-app`。`SYNC_CANARY` はリポジトリの変数で渡す）、配る前に見つける
